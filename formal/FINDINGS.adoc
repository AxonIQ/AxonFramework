= Axon Hunt -- Findings
:toc: left
:toclevels: 2
:icons: font

Living log of everything the hunt suite has found in Axon Framework 5. Entries are numbered
`F-<n>` and never renumbered.

[NOTE]
====
*The engine is never patched by this suite.* A confirmed defect gets an entry here with a candidate
fix, plus an expected-gap test that passes while the gap exists and flips red when it is closed. The
fix itself is a separate, reviewed change made by whoever owns the code.
====

Every entry carries how it was found. A finding discovered *by reading* is legitimate and is
labelled as such; it is weaker evidence than one a failing test produced, and saying so is the point
of the label.

Severity scale: *critical* (silent data loss or corruption in a documented configuration), *high*
(a documented guarantee does not hold), *medium* (a real defect with a narrow blast radius or an
easy workaround), *low* (a documentation or ergonomics gap).

== At a glance

|===

| *F-1* `SpringBootInvertsGapSettings`
| Under Spring Boot autoconfigure the JPA event store gets a 10-second gap timeout and a 60000-entry
  gap window, where the core defaults are 60 seconds and 10000. The two values are swapped.
| High
| Confirmed by reading. Open.

| `InMemoryTokenStore` implements no claim or ownership at all, and its Javadoc does not warn about

| A multi-event batch is not made visible atomically. A concurrent reader can observe a strict prefix

| Medium
| *Reproduced by test.* Open.

| *F-4* `ClaimExpiryReadsGlobalClock`
| Token-claim expiry is evaluated against a JVM-global clock, not a per-node injected one, so
  per-node clock skew cannot be simulated inside a single JVM.
| Low
| Confirmed by reading. Open, recorded as a harness constraint.

| *F-5* `SplitBlocksReclaimForAHardcodedMinute`
| A segment split blocks local re-claim of the segment for a hardcoded 60 seconds, not configurable
  and not scaled by any timescale setting.
| Low
| Confirmed by reading. Open.

| *F-6* `DefaultSequencingPolicyDegradesOnDcbStores`
| The wired default sequencing policy resolves from a resource that DCB-native stores never set, so
  on every DCB backend the default silently degrades to fully sequential single-key processing. The
  Javadoc names a different default.
| Medium
| *Reproduced by test*, and sharper than first written: every event lands in one segment, so the
  configured segment count buys nothing either. Open.

| *F-7* `EmptySequenceIdentifierThrows`
| `SimpleEventHandlingComponent` unwraps the sequencing policy's `Optional` with `get()`. Choosing
  `NoOpSequencingPolicy`, or `SequentialPerAggregatePolicy` on a DCB store, therefore throws
  `NoSuchElementException` on every event and the processor delivers nothing at all.
| High
| Reproduced by test. Open.

| *F-8* `RollbackAfterCommitIsUnspecified`
| The framework calls `AppendTransaction.rollback()` from a single per-transaction error handler
  whatever phase the error arrived in, so an error after a successful commit rolls back an already
  published batch. The contract does not say what that means.
| Low
| Reproduced by test. Open.

| *F-9* `ConcurrentStartupLosesInstances`
| Several processors starting at the same instant against a shared JDBC token store race to create the store's
  identifier row. One wins; the rest get a primary-key violation that the store turns into a startup failure instead
  of re-reading the row that now exists, so all but one instance fails to start. Measured: 3 of 4.
| High
| *Reproduced by test.* Open.

| *F-10* `ClaimProtocolToleratesNoStatedClockSkew`
| The claim protocol compares a timestamp one node wrote against another node's clock and states no tolerance for the
  two disagreeing. Measured: a node whose clock reads ahead takes a live claim up to that far early, so two nodes hold
  one segment for up to the skew, capped by one claim timeout. Nothing warns, and nothing in the protocol notices.
| Medium
| *Reproduced by test*, and quantified. Open.

| *F-11* `MergeRewindsToTheLowerOfTwoTokens`
| Merging two segments gives the merged one the lower of the two halves' tokens, so every event the further-ahead half
  had already handled is delivered again. The behaviour is deliberate and the documentation does not mention it.
| Medium
| *Reproduced by test.* Open.

| *F-12* `ResetDemandsAConverterItNeverUses`
| Rewinding a processor's tokens resolves a `GeneralConverter` out of the processing context in order to convert the
  reset context -- and does so even when there is no reset context. A processor wired over an application context that
  provides no components therefore cannot be reset at all, and fails with an error that says nothing about resets.
| Low
| *Reproduced by test.* Open.

| *F-15* `AggregateMarkerLowerBoundUnimplemented`
| Sourcing twice in one processing context on the aggregate-based JPA event store throws
  `UnsupportedOperationException: Not implemented yet`. The framework combines the two consistency markers with
  `lowerBound`, and the aggregate-based marker does not implement it. Ordinary event-sourced command handling reaches it.
| High
| *Reproduced by test*, on PostgreSQL, with a per-backend verdict vector. Open.

| *F-14* `UnconditionalAppendRejectedOnAggregateStore`
| An append made with no consistency condition is rejected as conflicting on the aggregate-based JPA event store
  whenever the tagged aggregate already holds events. The framework documents such an append as having conflict
  detection disabled entirely; on this engine it succeeds exactly once per aggregate and is refused for ever after, with
  an exception that tells the caller to retry.
| High
| *Reproduced by test*, on PostgreSQL, with a per-backend verdict vector. Open.

| *F-13* `AStalledHandlerKeepsItsClaims`
| A node frozen inside its event handler does not lose its segments: extending a claim is the coordinator's work, on a
  separate thread that keeps running. The classic stalled-owner failure therefore needs the whole process to stall, not
  just its handling, which is worth knowing before anybody writes a test for it.
| Low (not a defect)
| Measured. Recorded as a harness constraint.

| *F-16* `EventSkippedWhenItsTimestampAgesPastTheGapTimeout`
| An event whose transaction commits later than `gapTimeout` after the event's own message timestamp can be skipped by a
  streaming reader for ever. The reader decides whether to record a gap by comparing the event it can see against the
  wall clock, so a neighbour that has aged past the threshold suppresses the gap for the hole below it, and nothing ever
  asks for that index again.
| High
| *Reproduced by test*, on PostgreSQL, on both configuration paths. Open.

| *F-17* `DatabaseTransactionCommitRacesAppendTransactionCommit`
| On a store whose transaction lives on the processing context, the database transaction's commit and
  `EventStorageEngine.AppendTransaction.commit()` are two actions registered in the same lifecycle phase, and the
  framework runs same-phase actions with no ordering between them. An append's events were measured readable 1877ms
  before the `commit()` of the append that produced them was entered. Nothing in the interface says that `commit()` is
  not the durability point.
| Medium
| *Measured.* Open.

| *F-18* `ConnectorArtefactsCannotLinkAgainstThisReactor`
| No reachable Axon Server connector artefact can be loaded against this tree: the newest ones implement
  `EventStorageEngine.source(SourcingCondition)` and this reactor's interface requires
  `source(SourcingCondition, ProcessingContext)`. Loading one raises `AbstractMethodError` at run time, and `javac` does
  not catch it.
| Blocking (for coverage, not a defect)
| *Measured.* The Axon Server arm is blocked on it.

== F-1 -- Spring Boot autoconfigure inverts `gapTimeout` and `maxGapOffset`

*Severity:* High +
*Status:* Open. Confirmed by reading; no test exists yet. +
*Claims:* C14, M12 +
*Backend verdict vector:* `postgres-jpa:AFFECTED (Spring Boot path only)`, `in-memory:N/A`,
`axonserver:N/A`

=== What is wrong

The JPA event storage engine has two independent gap settings. `gapTimeout` is a duration in
milliseconds after which a recorded gap is dropped from a tracking token. `maxGapOffset` is a count:
how many positions ahead of a newly-seen index may be recorded as gaps.

The core configuration defaults them to 60000 ms and 10000 entries. The Spring Boot autoconfigure
properties default them to 10000 ms and 60000 entries. The two values are swapped, and the swapped
values are applied unconditionally.

=== Evidence

Core defaults:

* `eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/jpa/AggregateBasedJpaEventStorageEngineConfiguration.java:84` -- `DEFAULT_MAX_GAP_OFFSET = 10000`
* `eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/jpa/AggregateBasedJpaEventStorageEngineConfiguration.java:86` -- `DEFAULT_GAP_TIMEOUT = 60000`

Spring Boot defaults:

* `extensions/spring/spring-boot-autoconfigure/src/main/java/org/axonframework/extension/springboot/JpaEventStorageEngineConfigurationProperties.java:44` -- `@DefaultValue("10000") int gapTimeout`
* `extensions/spring/spring-boot-autoconfigure/src/main/java/org/axonframework/extension/springboot/JpaEventStorageEngineConfigurationProperties.java:46` -- `@DefaultValue("60000") int maxGapOffset`

Applied unconditionally:

* `extensions/spring/spring-boot-autoconfigure/src/main/java/org/axonframework/extension/springboot/autoconfig/JpaEventStoreAutoConfiguration.java:107` -- `.gapTimeout(properties.gapTimeout())`
* `extensions/spring/spring-boot-autoconfigure/src/main/java/org/axonframework/extension/springboot/autoconfig/JpaEventStoreAutoConfiguration.java:109` -- `.maxGapOffset(properties.maxGapOffset())`

=== Why it matters

The gap timeout is the window a not-yet-committed event has to become visible before a streaming
consumer stops looking for it. Shrinking it from 60 seconds to 10 makes it six times more likely
that a transaction outliving the window commits an event that is then never streamed to any
consumer, which is silent event loss on the read side. Widening `maxGapOffset` from 10000 to 60000
enlarges every tracking token by up to six times, which is a throughput and token-size cost rather
than a correctness one.

The direction of the error is the bad one: the setting that got smaller is the one guarding against
loss. And it applies to the configuration path most production applications use, since nearly every
Axon application on JPA is a Spring Boot application.

=== How it was found

By reading, during the claims-mining pass that preceded any test. The claim being verified was C14
("a gap older than `gapTimeout` is dropped from the token"), and checking the default value through
both configuration paths surfaced the disagreement. No test in the repository asserts that the two
paths produce the same engine.

=== Candidate fix

Swap the two `@DefaultValue` annotations in `JpaEventStorageEngineConfigurationProperties`, so that
`gapTimeout` defaults to `60000` and `maxGapOffset` to `10000`, matching the core configuration
record. One-line change on each of two lines; no behavioural change for anyone who set the
properties explicitly.

A durable guard is worth more than the fix: a test that builds the engine through both configuration
paths and asserts every effective setting is pairwise equal, or is listed in an explicit allow-list
of deliberate differences. That catches this whole class of silent configuration drift rather than
this one instance. Planned as scenario S19.

=== Reproduce

No automated reproduction yet. By inspection:

[source,bash]
----
grep -n 'DefaultValue' extensions/spring/spring-boot-autoconfigure/src/main/java/org/axonframework/extension/springboot/JpaEventStorageEngineConfigurationProperties.java
grep -n 'DEFAULT_GAP_TIMEOUT\|DEFAULT_MAX_GAP_OFFSET' eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/jpa/AggregateBasedJpaEventStorageEngineConfiguration.java
----

== F-2 -- `InMemoryTokenStore` implements no ownership, and does not say so

*Severity:* Medium +
*Status:* Open. Confirmed by reading. +
*Claims:* C18, C19, C20, C21, C22, M11

=== What is wrong

The `TokenStore` interface documents that fetching a token claims it for the current process,
"preventing access by other instances", that a claim may be taken only when the entry is unowned,
owned by the same node, or expired, and that extending a lost claim fails. `InMemoryTokenStore`
implements none of it. There is no owner field, no timestamp, no expiry.

=== Evidence

* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/token/store/inmemory/InMemoryTokenStore.java:126` -- `fetchToken` never fails on ownership
* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/token/store/inmemory/InMemoryTokenStore.java:140` -- `releaseClaim` is a documented no-op
* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/token/store/inmemory/InMemoryTokenStore.java:191` -- `fetchAvailableSegments` returns every segment, claimed or not
* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/token/store/inmemory/InMemoryTokenStore.java:50` -- the class Javadoc says only "thread-safe"

=== Why it matters

For the framework's users this is defensible: an in-memory store is not shared between processes, so
there is nothing to arbitrate. The defect is that the class does not say so. A reader comparing the
interface's contract against this implementation has no warning that five documented guarantees
simply do not apply.

For this suite it is a hard constraint. Any ownership assertion made against `InMemoryTokenStore`
passes vacuously, which is worse than no test at all, because it looks like coverage. Every
ownership scenario must run against a claim-capable store.

=== How it was found

By reading, while checking whether the planned multi-node layer could be built on the in-memory
store. It cannot.

=== Candidate fix

Documentation, not code. Add to the class Javadoc that this implementation provides no ownership
arbitration and that the claim-related guarantees of `TokenStore` do not hold for it, with a pointer
to the JDBC and JPA stores for any multi-process use.

=== Reproduce

[source,bash]
----
grep -n 'releaseClaim\|fetchAvailableSegments\|fetchToken' messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/token/store/inmemory/InMemoryTokenStore.java
----

== F-3 -- A committing batch is observable in part

*Severity:* Medium +
*Status:* Open. *Reproduced by test.* +
*Claims:* C9, C4, M17

=== What is wrong

`EventStorageEngine` documents that events "may only be visible to consumers after the invocation of
`commit()`". `InMemoryEventStorageEngine.commit()` inserts the batch one event at a time while
holding an append lock, but readers traverse the storage map without taking that lock. A reader
polling during a commit can therefore observe a strict prefix of a batch that has not finished
committing.

The documented guarantee is about the boundary between before-commit and after-commit. It says
nothing about atomicity *within* the commit, and the implementation does not provide it.

=== Evidence

* `eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/inmemory/InMemoryEventStorageEngine.java:127-146` -- per-event `eventStorage.put(next, event)` inside `appendLock`
* `eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/inmemory/InMemoryEventStorageEngine.java:290-306` -- `next()` reads `eventStorage.containsKey` with no lock
* `eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/EventStorageEngine.java:187` -- the guarantee, which is weaker than batch atomicity

=== Why it matters

A projection that assumes a multi-event transaction arrives whole will see a torn state. Whether
that matters depends on the projection, but the framework gives no way to tell that a batch is
incomplete, so a consumer cannot defend against it.

=== How it was found

By reading, during the claims-mining pass. The `DcbStoreModel` reference model does not reproduce
it, and cannot: the model is sequential, so it has no notion of a reader observing an operation
mid-flight. `ModelAndInMemoryEngineAgreeTest` applies operations one at a time to both sides and is
therefore structurally unable to see this divergence. That is a stated boundary of the model rather
than a gap in it, and it is why the finding is not yet reproduced.

=== Candidate fix

Two shapes are plausible, and choosing between them is a design decision for the framework's owners
rather than for this suite. Either publish the batch under a single visible-position advance, so
readers see a position boundary rather than individual map entries, or state explicitly in
`EventStorageEngine`'s contract that a batch is not atomically visible and that consumers must not
assume it is.

=== What the reproduction observed

The scenario `partial_batch_never_visible_to_concurrent_reader` puts one writer committing
hundred-event batches next to one reader reading the whole store as fast as it can, and counts, per
single read, how many of each batch were visible in that read. A count strictly between one and a
hundred is a batch caught half-written.

Five consecutive runs of the arm, on the same machine, one after another:

[source]
----
run 1  polls=8707  torn observations=12
run 2  polls=6410  torn observations=32
run 3  polls=4904  torn observations=15
run 4  polls=7261  torn observations=19
run 5  polls=7343  torn observations=20
----

Sample observations from one run, as recorded in the history under the `poll` operation:

[source]
----
{observed={b0=1},  batchSize=100}
{observed={b1=1},  batchSize=100}
{observed={b1=41}, batchSize=100}
----

Inside a full run of the suite, where the JVM is warm and the writer is faster, the rate holds but
the absolute count is lower -- 9 torn observations out of 5310 reads across the arm's three seeds.
The arm runs three seeds rather than one for exactly that reason: roughly one read in four hundred
catches a batch half-written, so a single run is too thin a sample to depend on.

A reader that could see event `b1-e0` through `b1-e40` and nothing beyond, while the writer was
still inserting `b1-e41` onwards, is precisely the strict prefix the finding predicted. The
mechanism is confirmed by the code path as well: `source(...)` snapshots the stream's end position
from `eventStorage.lastKey()` at the moment the stream is opened, so a stream opened mid-commit ends
at whatever position the writer had reached.

Two neighbouring facts were asserted alongside, so the finding is not read as stronger than it is.
Nothing is delivered before its commit -- `NoVisibilityBeforeCommit` held on every run -- and the
tear is transient: the authoritative scan taken after the run had quiesced held every batch whole,
one hundred events each, with none missing. The gap is in the atomicity of a batch's *arrival*, not
in what the store ends up holding.

=== Reproduce

[source,bash]
----
./mvnw -Phunt -pl simulation -am test -Dtest=PartialBatchVisibilityTest \
    -Dsurefire.failIfNoSpecifiedTests=false
----

The test asserts that a torn observation *is* found, because the suite records the framework's
current behaviour and never patches it. It is documented to flip red the day batch visibility
becomes atomic, and that flip is the signal to re-evaluate this entry and turn the assertion around.

== F-4 -- Token-claim expiry reads a JVM-global clock

*Severity:* Low +
*Status:* Open. Confirmed by reading. +
*Claims:* C20, M3

=== What is wrong

Whether a token claim has expired is decided by comparing a stored timestamp against
`ClockUtils.instant()`, which reads a single static `AtomicReference<Clock>` shared by the whole
JVM. There is no per-node clock on that path, even though other parts of the processor take an
injected `Clock`.

=== Evidence

* `common/src/main/java/org/axonframework/common/ClockUtils.java:49` -- `private static final AtomicReference<Clock> CLOCK`
* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/token/store/jpa/TokenEntry.java:159-160` -- `expired()` reads `ClockUtils.instant()`
* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/pooled/SplitTask.java:113` -- by contrast, uses an injected `clock` field

=== Why it matters

For the framework, this is a documentation gap: nothing states what clock skew between nodes the
claim protocol tolerates, and the expiry check compares a remotely-written timestamp against the
local clock with no stated allowance.

For this suite it is a determinism-seam constraint. Two "nodes" in one JVM cannot be given different
clocks through this path, so any scenario that needs per-node skew must either use a claim-aware
fake token store whose expiry reads an injected clock, or run the nodes in separate processes.

=== How it was found

By reading, while mapping the injectable seams available for the multi-node layer.

=== Candidate fix

Two independent improvements. Document the tolerated clock skew for the claim protocol, since a
protocol that compares timestamps written by different machines needs a stated bound. Separately,
route the expiry check through an injectable clock so that skew is testable at all; that is a wider
change than this suite should propose without the framework's owners weighing in.

=== Reproduce

[source,bash]
----
grep -n 'ClockUtils.instant' messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/token/store/jpa/TokenEntry.java
grep -n 'AtomicReference<Clock>' common/src/main/java/org/axonframework/common/ClockUtils.java
----

== F-5 -- A split blocks re-claim for a hardcoded minute

*Severity:* Low +
*Status:* Open. Confirmed by reading. +
*Claims:* M10

=== What is wrong

When a processor splits a segment, it blocks its own coordinator from re-claiming that segment for
60 seconds. The duration is a literal in the code, not a configuration setting, and it does not
scale with any of the processor's other timing settings.

=== Evidence

* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/pooled/SplitTask.java:113` -- `clock.instant().plusSeconds(60)`

The guard is also stored in a per-coordinator map, so it constrains only the splitting node; nothing
stops another node claiming the segment mid-split.

=== Correction, found by reading the same file more carefully while budgeting the split scenario

The sixty seconds is a ceiling, not the duration. `SplitTask.splitAndRelease` removes the segment from
`releasesDeadlines` in a `whenComplete` block, so a split that completes clears its own guard
(`messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/pooled/SplitTask.java:141-143`),
and `MergeTask` does the same for both halves (`MergeTask.java:177-178`). The block therefore lasts as long as the
instruction takes, and the minute only applies to a split that never finishes. The operational impact is far smaller
than this entry originally claimed, and the measured consequence for a time-compressed suite is a delay of hundreds of
milliseconds rather than a minute: the split-and-merge storm ran seven splits and seven merges per seed inside a
four-second window with no segment left unclaimable. What remains true is that the duration is a literal, that it does
not scale with any other setting, and that the guard is per-coordinator.

=== Why it matters

Two consequences. Operationally, a split costs a minute of unavailability for that segment on the
splitting node regardless of how fast the split actually completed. For this suite, any scenario
running with compressed timeouts has a 60-second term that does not compress, which will look like a
liveness violation to a naive horizon.

=== How it was found

By reading, while budgeting the split and merge scenarios.

=== Candidate fix

Derive the block from `tokenClaimInterval` (or make it a configuration setting defaulting to the
current value) so that a time-compressed configuration compresses it too. Separately, the per-node
scope of the guard is worth documenting, since it reads as a global exclusion and is not one.

=== Reproduce

[source,bash]
----
grep -n 'plusSeconds(60)' messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/pooled/SplitTask.java
----

== F-6 -- The wired default sequencing policy does not match the documented one, and degrades on DCB stores

*Severity:* Medium +
*Status:* Open. *Reproduced by test.* +
*Claims:* C32, M14

=== What is wrong

`SequencingPolicy`'s Javadoc names `SequentialPerAggregatePolicy` as the default event-processing
policy. The wired default is a hierarchical policy that tries `SequentialPerAggregatePolicy` first
and falls back to `SequentialPolicy`. `SequentialPerAggregatePolicy` resolves its key from a legacy
aggregate-identifier resource, which DCB-native stores never populate. On every DCB backend the
fallback therefore always wins, and the effective default is fully sequential processing of the
whole segment under a single key.

=== Evidence

* `messaging/src/main/java/org/axonframework/messaging/core/sequencing/SequencingPolicy.java:34-35` -- the documented default
* `messaging/src/main/java/org/axonframework/messaging/eventhandling/SimpleEventHandlingComponent.java:61-64` -- the wired default
* `messaging/src/main/java/org/axonframework/messaging/core/sequencing/SequentialPerAggregatePolicy.java:47` -- resolves from `LegacyResources.AGGREGATE_IDENTIFIER_KEY`

=== Why it matters

A user who reads the Javadoc expects per-aggregate parallelism within a segment and gets none. On a
DCB backend the same application processes its segment strictly one event at a time. That is safe,
and it is a throughput cliff nobody was told about. The behaviour also differs between the
aggregate-based JPA backend, where the legacy resource is populated, and every DCB backend, where it
is not, so the same configuration behaves differently depending on the store.

=== How it was found

By reading, while designing the ordering scenarios. It changed the design: the planned "empty policy
means parallel" arm was testing a policy that is not the default.

=== Candidate fix

At minimum, correct the Javadoc on `SequencingPolicy` to name the hierarchical policy that is
actually wired, and state that its per-aggregate half is inert on stores that do not populate the
aggregate-identifier resource. The larger question, whether DCB-native stores should populate an
equivalent resource so that per-key parallelism is available by default, is a design decision for
the framework's owners.

=== What the reproduction observed, and the part that was missed by reading

The scenario `sequencing_policy_order_preserved_wired_default` writes one hundred and eighty events
across six independent streams, with four segments and four workers configured, and records the
sequence identifier the framework resolved for every delivery. The run's read-model state:

[source]
----
{"unresolvedSequenceKeys": 0, "deliveredEvents": 180, "arm": "wired-default", "distinctSequenceKeys": 1}
----

One distinct identifier for one hundred and eighty events over six streams. The ordering oracle
`SequenceKeyOrderPreserved` held, which it must: with one identifier, per-key order is global order.

The consequence found by testing rather than by reading is worse than the entry originally said. A
segment is chosen by hashing the sequence identifier
(`MSG/.../segmenting/SegmentMatcher.java:65`, reached from
`MSG/eventhandling/processing/ProcessorEventHandlingComponents.java:193-198`), so one identifier
means one hash, which means **one segment**. Configuring four segments and four workers on a
DCB-native store does not merely fail to parallelise within a segment; three of the four segments
receive nothing at all. The throughput cliff is a factor of the segment count, not a factor of one.

=== Reproduce

[source,bash]
----
./mvnw -Phunt -pl simulation -am test -Dtest=SequencingPolicyOrderTest \
    -Dsurefire.failIfNoSpecifiedTests=false
----

By inspection:

[source,bash]
----
grep -n 'Default event processing policy' messaging/src/main/java/org/axonframework/messaging/core/sequencing/SequencingPolicy.java
sed -n '55,70p' messaging/src/main/java/org/axonframework/messaging/eventhandling/SimpleEventHandlingComponent.java
grep -n 'AGGREGATE_IDENTIFIER_KEY' messaging/src/main/java/org/axonframework/messaging/core/sequencing/SequentialPerAggregatePolicy.java
----

== F-7 -- An unresolvable sequence identifier throws, and stops the read side dead

*Severity:* High +
*Status:* Open. Reproduced by test. +
*Claims:* C32, C33, C34, M14

=== What is wrong

`SequencingPolicy.sequenceIdentifierFor` returns an `Optional`, and its own Javadoc says an empty
result means the policy cannot determine an identifier and that "it is up to the component using
this policy to provide a default behavior, use another policy, throw an exception or react in any
other way -- as appropriate".

`SimpleEventHandlingComponent` unwraps it with `get()`. Two policies the framework ships return an
empty `Optional` in ordinary use, and both therefore make every single event throw
`NoSuchElementException` before it can be handled:

* `NoOpSequencingPolicy`, whose entire purpose is to impose no sequencing, and whose Javadoc says
  infrastructure "may decide upon this sequencing policy being present bypassing sequencing
  infrastructure at all";
* `SequentialPerAggregatePolicy` used on its own against any store that does not populate
  `LegacyResources.AGGREGATE_IDENTIFIER_KEY`, which is every DCB-native store (finding F-6).

The framework contains the graceful handling of the same situation a few classes away.
`SegmentMatcher.sequenceIdentifier` resolves the identical `Optional` with
`.orElseGet(event::identifier)`. Two components, one situation, opposite answers.

=== Evidence

* `messaging/src/main/java/org/axonframework/messaging/eventhandling/SimpleEventHandlingComponent.java:169-185` -- `@SuppressWarnings("OptionalGetWithoutIsPresent")` over two `get()` calls
* `messaging/src/main/java/org/axonframework/messaging/eventhandling/SimpleEventHandlingComponent.java:176` -- `return sequencingPolicy.sequenceIdentifierFor(event, context).get();`
* `messaging/src/main/java/org/axonframework/messaging/eventhandling/SimpleEventHandlingComponent.java:184` -- `.orElse(sequencingPolicy.sequenceIdentifierFor(event, context).get())`
* `messaging/src/main/java/org/axonframework/messaging/core/sequencing/NoOpSequencingPolicy.java:47-50` -- returns `Optional.empty()`
* `messaging/src/main/java/org/axonframework/messaging/core/sequencing/SequentialPerAggregatePolicy.java:47` -- returns `Optional.ofNullable(context.getResource(LegacyResources.AGGREGATE_IDENTIFIER_KEY))`
* `messaging/src/main/java/org/axonframework/messaging/core/sequencing/SequencingPolicy.java:76-81` -- the contract the `get()` breaks
* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/segmenting/SegmentMatcher.java:78` -- the same resolution, handled gracefully

Line 184 carries a second, independent defect. `Optional.orElse` evaluates its argument eagerly, so
the fallback `get()` runs even when a sub-component did resolve an identifier. A component whose
handlers include another `EventHandlingComponent` therefore throws anyway, although the value it
would have returned was available.

=== Why it matters

It is silent and total. There is no configuration error, no startup failure and no rejected
registration: the processor starts, claims its segments, and then throws on every event for ever.
One measured run threw two thousand two hundred and four times in eight seconds and delivered
nothing, because the coordinator retries a work package that failed.

`NoOpSequencingPolicy` is the more serious of the two, because choosing it is a deliberate,
documented act. A user who reads its Javadoc and selects it gets a projection that never advances.

=== How it was found

By testing. The scenario arms were written from the plan's expectation that these policies would
yield "empty sequence identifiers" and that the run would exhibit unsequenced handling. What the
arms actually observed was no handling at all.

=== Candidate fix

Resolve the `Optional` rather than unwrap it. `SegmentMatcher` already shows the shape:
`.orElseGet(event::identifier)` gives every event its own identifier, which is the natural reading
of "no sequencing requirements for the handling of this message". Whatever default is chosen, both
call sites need it, and the eager `orElse` on the second one must become `orElseGet` so the fallback
is not evaluated when a sub-component answered.

A test asserting that every shipped `SequencingPolicy` can be handed to
`SimpleEventHandlingComponent.create` and produce a working processor would catch the whole class.

=== Reproduce

[source,bash]
----
./mvnw -Phunt -pl simulation -am test -Dtest=SequencingPolicyOrderTest \
    -Dsurefire.failIfNoSpecifiedTests=false
----

The `no-op` and `per-aggregate` arms both record `deliveredEvents: 0` and a `sequence` note carrying
`java.util.NoSuchElementException`, and both runs report `INCONCLUSIVE`: nothing was found broken,
and a read side that never ran cannot be reported as a pass.

== F-8 -- Rollback after a successful commit is unspecified, and is requested anyway

*Severity:* Low +
*Status:* Open. Reproduced by test. +
*Claims:* C29

=== What is wrong

`AppendTransaction.rollback()` is documented as rolling "back any events that have been appended,
permanently making them unavailable for consumers". Nothing says what it means once `commit()` has
succeeded, and no implementation can honour that wording at that point: the batch is published.

`DefaultEventStoreTransaction` registers exactly one error handler per transaction and calls
`rollback()` from it regardless of which phase the error arrived in. An error in the
`AFTER_COMMIT` phase -- which is where the transaction is asked for its consistency marker, strictly
after the commit -- therefore produces a rollback of a batch the store has already made visible.

=== Evidence

* `eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/EventStorageEngine.java:204` -- the wording
* `eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/EventStorageEngine.java:209-215` -- `afterCommit` is documented as called only after a successful commit
* `eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/DefaultEventStoreTransaction.java:210-214` -- one `onError` handler, registered alongside the commit step, calling `tx.rollback()`
* `eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/inmemory/InMemoryEventStorageEngine.java:157-160` -- the in-memory engine's `rollback()` only marks the transaction finished, so a post-commit rollback is a silent no-op

=== Why it matters

Mostly for whoever writes the next storage engine. The in-memory engine does the right thing by
accident: its `rollback()` cannot un-publish, so it does nothing. An engine that took the wording
literally and tried to delete the batch would destroy committed, already-delivered events because a
marker calculation failed.

It matters for this suite too, and that is how it was found. An oracle reading the rollback record
naively reports every committed event of such a transaction as observable-after-rollback, which is
a false finding with a very convincing message attached.

=== How it was found

By testing, while building the third arm of
`uncommitted_never_visible_rolledback_never_delivered`. The arm injects a failure in the
`AFTER_COMMIT` phase, and the first run reported a rolled-back transaction whose events were both
delivered and present in the store.

=== Candidate fix

Documentation first: state on `AppendTransaction.rollback()` that it is only meaningful before
`commit()` has completed, and that after a successful commit it must be a no-op. Then, optionally,
stop asking: `DefaultEventStoreTransaction` knows whether the commit completed, so its error handler
can skip the rollback once it has.

=== Reproduce

[source,bash]
----
./mvnw -Phunt -pl simulation -am test -Dtest=TransactionPhaseFailureTest \
    -Dsurefire.failIfNoSpecifiedTests=false
----

The after-commit arm asserts that a rollback was requested and carried `afterCommit=true`, and that
the committed events stayed in the store. The harness records such a rollback as having discarded
nothing, keeping the offered identifiers under `offeredEventIds`, which is what keeps
`RolledBackEventsNeverObservable` a real oracle instead of a source of false alarms.

== F-9 -- Starting several processors at once against a shared JDBC token store loses all but one

*Severity:* High +
*Status:* Open. *Reproduced by test.* +
*Claims:* C18, C36, M16 +
*Backend verdict vector:* `hsqldb-tokens:FAIL`, `in-memory:N/A (the in-heap token store keeps no identifier row)`

=== What is wrong

Starting a `PooledStreamingEventProcessor` begins by asking its token store for a storage identifier. A
`JdbcTokenStore` keeps that identifier in a row of the token table and creates it lazily, the first time anybody asks:
it selects the row, and inserts one if the select found nothing.

That read-then-write is not atomic and is not guarded. When several instances of an application start at the same
instant against the same token table, several of them select nothing and several of them insert the same primary key.
One insert wins. Every other gets a constraint violation, which `initializeConfigToken` wraps in an
`UnableToRetrieveIdentifierException` and rethrows -- without re-reading the row that, by then, definitely exists.
`PooledStreamingEventProcessor.start()` chains straight off that call, so the future it returns completes
exceptionally and the processor never starts.

The exception's own message is `"Exception while attempting to initialize the config token. It may have been
concurrently initialized."` The race was anticipated at the point where it is thrown and is still allowed to reach the
caller.

=== Evidence

* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/token/store/jdbc/JdbcTokenStore.java:161-169` -- `retrieveStorageIdentifier` selects, then initialises when the select found nothing
* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/token/store/jdbc/JdbcTokenStore.java:183-195` -- `initializeConfigToken` catches the `SQLException` and rethrows it as `UnableToRetrieveIdentifierException`, with no re-read
* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/pooled/PooledStreamingEventProcessor.java:189-195` -- `start()` is `unitOfWork.executeWithResult(tokenStore::retrieveStorageIdentifier).thenAccept(...).thenCompose(...)`, so the failure fails the start
* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/token/store/jpa/JpaTokenStore.java` -- the JPA store keeps the same config-token design, so the same race is expected there; not measured

=== Why it matters

This is the first-deploy and rolling-restart case, and it is exactly the deployment shape the token store exists for.
Bring four instances of an Axon application up together against a fresh database and three of them fail to start.
There is no retry, no warning and no degraded mode: `start()` completes exceptionally, and what happens next is
whatever the surrounding application does with a failed startup. A supervised deployment restarts the failed
processes and recovers on the second attempt, which is why this can go unnoticed in production and show up only as
"the first deploy always flaps".

It also blocks anything downstream of it from being tested. Because it serialises the boot, the segment-creation race
that follows never happens: one node comes up while the others are failing, and it has created every segment by the
time they retry.

=== How it was found

By testing. The scenario `concurrent_bootstrap_initializes_segments_exactly_once` boots four nodes from a barrier
against an empty store, and the first run of it did not reach its oracles at all -- three of the four processors
threw out of `start()`. The stack ended in an HSQLDB `SQLIntegrityConstraintViolationException` on `TOKENENTRY`.

=== Candidate fix

Re-read on conflict. `initializeConfigToken` already knows the insert failed because somebody else got there first;
selecting the row again and returning it is the whole fix, and it is three lines:

[source,java]
----
private ConfigToken initializeConfigToken(Connection connection) {
    try {
        return (ConfigToken) insertTokenEntry(connection, new ConfigToken(...), CONFIG_TOKEN_ID, CONFIG_SEGMENT);
    } catch (SQLException e) {
        ConfigToken concurrent = retrieveConfigToken(connection);
        if (concurrent != null) {
            return concurrent;
        }
        throw new UnableToRetrieveIdentifierException("...", e);
    }
}
----

The same treatment belongs on the JPA store. A durable guard is worth more than either: a test that starts N
processors simultaneously against one token store and asserts that all N come up.

=== Reproduce

[source,bash]
----
./mvnw -Phunt -pl simulation -am test -Dtest=ClaimCapableBackendTest \
    -Dsurefire.failIfNoSpecifiedTests=false
----

Measured output: `F-9: 3 of 4 simultaneous storage-identifier resolutions failed`.

The test asserts that at least one of the four fails, because the suite records the framework's current behaviour and
never patches it. It flips red the day a simultaneous boot stops costing instances, and that flip is the signal to
close this entry rather than a test to repair.

=== What the harness does about it, and why that is not a fix

`HuntWorld` resolves the storage identifier once, on one node, before releasing the others from the boot barrier, and
`HuntNode` records a failed start and gives the node one more try. Neither touches framework code. The first is there
because without it the segment-creation race is unreachable -- every multi-node scenario would stop at this one
defect instead of testing what it was written for. The second is what a supervised deployment does with a process
that died on startup. Both are stated here so that nobody reads a green cluster run as evidence that F-9 is closed:
the only thing that closes it is the expected-gap test above going red.

== F-10 -- The claim protocol states no tolerance for clock skew, and tolerates none

*Severity:* Medium +
*Status:* Open. *Reproduced by test*, and quantified. +
*Claims:* C19, C20, C22, M3 +
*Backend verdict vector:* `hsqldb-tokens:AFFECTED`, `in-memory:N/A (the in-heap token store has no expiry to compare)`

=== What is wrong

Whether a claim may be stolen is the inequality `timestamp + claimTimeout < now`. The timestamp is written by whichever
node last touched the row; `now` is read by whichever node is asking. The two are different machines in every deployment
the token store exists for, and nothing in the framework states how far apart their clocks may be. Searching `skew`,
`clockSkew` and `clock skew` across the token-store packages and the streaming-processor reference page returns nothing.

=== Evidence

* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/token/store/jdbc/JdbcTokenEntry.java:202-207` -- `mayClaim` and `expired`, the whole of the arbitration
* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/token/store/jpa/TokenEntry.java:159-161` -- the same comparison on the JPA store
* `docs/reference-guide/modules/events/pages/event-processors/streaming.adoc` -- documents the ten-second claim timeout and says nothing about the clocks it is measured with

=== What the reproduction measured

The scenario `at_most_one_segment_owner_with_skew_none` and its two skewed siblings run four nodes over sixteen segments
against the claim-capable store, with one node's view of that store configured to treat a claim as expired earlier than
the run's claim timeout says. That is not an approximation: a node whose clock reads `delta` ahead evaluates
`timestamp + claimTimeout < now + delta`, which is the same inequality as `timestamp + (claimTimeout - delta) < now`, so
shortening one node's claim timeout reproduces its decisions exactly. What it does not model is the timestamp that node
*writes*, which a real skewed clock would also shift; that is unreachable, because the framework stamps a claim from a
process-global clock every node in one virtual machine shares (finding F-4).

Measured against a two-second claim timeout and a four-hundred-millisecond extension threshold:

[source]
----
skew 0ms     widest overlap  none          9 claim handovers across 3 seeds, all orderly
skew 1000ms  widest overlap  964 - 992ms   inside the declared tolerance of 1000ms
skew 4000ms  widest overlap  478 - 1692ms  16 to 32 AtMostOneSegmentOwner violations
----

Three things follow, and the third is the one worth acting on.

*The overlap is bounded by the skew.* A node reading `delta` ahead can take a claim at most `delta` before it would have
lapsed anyway, so the overlap can never exceed `delta` -- which the middle arm asserts and the oracle judges.

*It is also bounded by one claim timeout.* At four seconds of skew against a two-second timeout the overlap saturates:
the measured worst case is 1692ms, not 4000ms. The loser's own claim still lapses one timeout after its last refresh
however far ahead the thief's clock reads, because only the comparison is skewed and not the timestamp.

*A skew smaller than the margin between the claim timeout and the owner's refresh rate is invisible.* An owner refreshes
its row with every batch it stores and, when idle, on every extension threshold. With a two-second timeout and a
four-hundred-millisecond threshold, a row is rarely more than four hundred milliseconds old, so a clock a second ahead
usually finds nothing to take -- and occasionally does, which is why the middle arm's measured overlap sits just under
its bound rather than at zero. The tolerated skew is therefore not zero and not the claim timeout: it is
`claimTimeout - refreshInterval`, a quantity no configuration names and no document states.

=== Why it matters

Two nodes holding one segment for up to a claim timeout means two nodes processing the same events for that long. The
framework's own answer to a stolen claim is that the loser's token write fails and its batch rolls back, so effects
already applied are repeated -- which is the documented at-least-once behaviour and is fine for an idempotent handler and
not fine for anything else. What is missing is any statement of how much clock disagreement it takes to get there.

=== Candidate fix

Document the bound. The claim protocol tolerates skew up to the margin between the claim timeout and the rate at which an
owner refreshes its claim, and produces overlapping ownership of up to one claim timeout beyond it; an operator sizing
`claimTimeout` and `claimExtensionThreshold` needs that sentence to size them safely. Separately, the expiry comparison
could carry an explicit tolerance so that the bound is a setting rather than an emergent property of two other settings.

=== Reproduce

[source,bash]
----
./mvnw -Phunt -pl simulation -am test -Dtest=SegmentOwnershipUnderSkewTest \
    -Dsurefire.failIfNoSpecifiedTests=false
----

The double-timeout arm asserts that ownership *is* broken, because the suite records the framework's current behaviour
and never patches it. It flips red the day the claim protocol gains a stated tolerance wide enough to cover it, and that
flip is the signal to revisit this entry.

== F-11 -- A merge rewinds to the lower of the two tokens, and nothing says so

*Severity:* Medium +
*Status:* Open. *Reproduced by test.* +
*Claims:* C24, C25, C38, M10

=== What is wrong

`MergeTask` merges two segments by giving the surviving one the lower of the two halves' tracking tokens. Every event the
further-ahead half had already handled therefore sits above the merged segment's position and is delivered again. The
behaviour is deliberate -- taking the higher token would skip events the lower half had not reached -- and it is the right
choice. What is missing is any statement of it: `Segment`'s Javadoc describes the mask algebra, `MergeTask`'s describes
when a merge succeeds, and neither mentions that a merge redelivers.

=== Evidence

* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/pooled/MergeTask.java:126-133` -- both tokens fetched, then merged lower-first
* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/segmenting/Segment.java:141-142` -- the documented merge precondition, which is about masks and not about positions

=== What the reproduction observed

`split_merge_no_loss_no_dup_under_load` splits and merges a segment repeatedly while the workload writes, seven times per
seed inside a four-second window. Before the delivery oracle was taught about it, the arm reported repeated deliveries
outside every claim-transition and node-recovery window -- events like `writer-7-327-w` arriving twice with nothing in the
history that licensed it. The mechanism is the merge, and the events repeated are exactly the ones between the two halves'
tokens.

Nothing is lost: the union of deliveries across every segment epoch still covers every committed event, and the ledger's
conservation law holds once the projection is idempotent -- which the framework's own documentation requires of a handler
in a split-resource deployment.

=== Why it matters

A projection that is not idempotent double-applies on every merge. The framework already tells users to make handlers
idempotent for the split-resource deployment, so the requirement is not new; what is new is that a merge triggers it
even on a cluster that never lost a claim and never crashed. An operator who split segments to add throughput and then
merged them back has redelivered part of the stream, and nothing warned them.

=== Candidate fix

Documentation. State on `StreamingEventProcessor.mergeSegment` and on the reference page that a merge resumes from the
lower of the two segments' positions, so events already handled by the further-ahead half are handled again, and that
handlers must therefore be idempotent across a merge regardless of the token store's deployment.

=== Reproduce

[source,bash]
----
./mvnw -Phunt -pl simulation -am test -Dtest=SplitAndMergeUnderLoadTest \
    -Dsurefire.failIfNoSpecifiedTests=false
----

`DeliveryChecker` now opens a licence window at every recorded split and merge, so the arm passes and reports the
repeats as a distribution rather than as a violation. Removing that licence turns the finding back into a red run, which
is how it was found.

== F-12 -- Resetting tokens demands a converter even when there is nothing to convert

`PooledStreamingEventProcessor.resetTokens` converts the reset context to a byte array through a `GeneralConverter` it

== F-13 -- A node stalled in event handling keeps every claim it holds

*Severity:* Low, and not a defect +
*Status:* Measured. Recorded as a harness constraint. +
*Claims:* C20, C21, M1

=== What was expected, and what happens

The classic lease failure is a process that stalls -- a garbage-collection pause, a frozen virtual machine -- long enough
for its claims to expire, and then wakes up mid-batch into a cluster that has reassigned its work. A suite that only
kills processes never visits it, which is why this one has a stall seam.

The stall this suite can reach is inside the event handler, and it does not produce that state. Extending a claim is the
coordinator's work, on a thread of its own, and the coordinator keeps running while the handler is frozen: it calls
`WorkPackage.extendClaimIfThresholdIsMet()` for every package it holds on every coordination cycle. The frozen node's
rows therefore stay fresh for as long as the freeze lasts, and nothing expires.

=== Evidence

* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/pooled/Coordinator.java:814` -- the coordinator extending its packages' claims
* `messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/pooled/WorkPackage.java:470-479` -- the extension, in its own unit of work, independent of any batch

=== Consequences

For the framework this is correct and arguably better than the alternative: the process is alive, so its claims are
alive. It is worth documenting, because the reference page's account of claim stealing reads as though a slow owner loses
its segments, and a slow *handler* does not.

For this suite it is a constraint on what the pause seam can test. Reaching the stalled-owner state needs the whole
process stalled -- which, in one virtual machine, means stalling the node's access to the token store as well as its
handling. The ownership scenario therefore uses a node crash to lapse a claim, and carries no stall window: a fault that
cannot take a segment away, and that lands only while the node is still handling events, is noise rather than evidence.

=== Reproduce

By inspection:

[source,bash]
----
grep -n 'extendClaimIfThresholdIsMet' messaging/src/main/java/org/axonframework/messaging/eventhandling/processing/streaming/pooled/Coordinator.java
----

== F-14 -- An unconditional append is rejected as conflicting on the aggregate-based store

*Severity:* High +
*Status:* Open. *Reproduced by test.* +
*Claims:* C2, C10 +
*Backend vector:* `in-memory:PASS hsqldb-tokens:PASS postgres-jpa:FAIL postgres-jpa-split-tokens:FAIL`

=== What is wrong

`AppendCondition.none()` is the framework's way of appending without a consistency condition, and the documentation is
explicit about what it means: conflict detection is disabled entirely, its marker is `INFINITY`, and the conflict check
short-circuits. On the aggregate-based JPA event store it does not mean that. The engine derives each event's aggregate
sequence number from the append condition's marker, and an `INFINITY` marker carries no position for any aggregate, so
the sequencer starts that aggregate at sequence `0`. For an aggregate that already holds events, inserting sequence `0`
again violates the unique constraint the engine relies on as its conflict check, and the failure is translated into
`AppendEventsTransactionRejectedException` -- the framework's own "you conflicted, source again and retry" answer, for an
append that asked for no consistency at all. The retry then fails identically, for ever.

The same line treats `ORIGIN` and `INFINITY` as the same thing, so "append with no condition" and "append only if this
aggregate is empty" are indistinguishable on this engine.

=== Evidence

* `eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/AggregateBasedConsistencyMarker.java:72-74` --
  `else if (consistencyMarker == ORIGIN || consistencyMarker == INFINITY) { return new
  AggregateBasedConsistencyMarker(Map.of()); }`, an empty map of aggregate positions for both sentinels
* `eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/jpa/AggregateBasedJpaEventStorageEngine.java:248-256`
  -- the entry's sequence number comes from `sequencer.incrementAndGetSequenceOf(aggregateIdentifier)`, which for an
  empty marker starts at `0`
* `eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/AggregateBasedEventStorageEngineUtils.java:104-124`
  -- the duplicate-key violation is translated into `AppendEventsTransactionRejectedException`
* `eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/NoAppendCondition.java:42-44` -- the
  documented `INFINITY` marker of `AppendCondition.none()`

=== What the reproduction observed

The ledger workload's `rebalance` command appends without sourcing, which is exactly how the framework produces an
unconditional append. Run unchanged against both PostgreSQL arms, `AppendOutcomeChecker` raised 231 and 259
`UnconditionalAppendNeverRejected` violations respectively, all of the form "an append anchored at the end of the stream
was rejected as conflicting". The same scenario, the same workload and the same oracle raise nothing on either store that
speaks the Dynamic Consistency Boundary protocol, which is what makes the vector an attribution rather than an argument.

=== Why it matters

An unconditional append is the documented way to write an event that takes part in nobody's consistency boundary, and
users reach for it precisely where they do not want a conflict check. On this engine it works for the first event of an
aggregate and never again, and the error it raises is the one that tells the caller the write is safe to retry after
re-sourcing. A projection-driven or reference-data write path built on `AppendCondition.none()` therefore appears to
work on an in-memory or Dynamic Consistency Boundary store and stops working on the JPA engine, with an exception that
names a conflict that does not exist.

=== Candidate fix

An `INFINITY` marker must mean "append at the end", not "append at sequence zero". Resolve each tagged aggregate's
current highest sequence number before assigning, for an unconditional append only, and let the append take the next
sequence for each. `ORIGIN` must keep its current behaviour -- starting at zero is precisely what "the aggregate must be
empty" means -- so the two sentinels have to stop sharing a branch. Alternatively, if an aggregate store genuinely cannot
honour an unconditional append, the engine should reject it with an exception that says so rather than with a conflict
its caller will retry.

=== Reproduce

[source,bash]
----
./mvnw -Phunt -pl simulation -am test -Dhunt.excludedGroups=fuzz -Dtest=BackendDifferentialTest \
    -Dsurefire.failIfNoSpecifiedTests=false
----

The run prints one `VECTOR` line per scenario. The finding is the `postgres-jpa:FAIL` entries against `in-memory:PASS`.

== F-15 -- Sourcing twice in one processing context throws on the aggregate-based store

*Severity:* High +
*Status:* Open. *Reproduced by test.* +
*Claims:* C5, C6, C7 +
*Backend vector:* `in-memory:PASS postgres-jpa:FAIL`

=== What is wrong

`DefaultEventStoreTransaction` combines consistency markers when a processing context sources more than once: the first
sourcing's marker is kept as the append position, and every later one is folded in with `lowerBound`, because the lower of
the two is the safe anchor. `AggregateBasedConsistencyMarker.doLowerBound` throws
`UnsupportedOperationException("Not implemented yet")`, so on the aggregate-based JPA event store the second sourcing in a
processing context fails outright.

This is not an exotic path. A command handler that loads two entities, or one that loads the same entity twice, or a
multi-entity handling component, sources twice by construction, and none of that is unusual or discouraged.

=== Evidence

* `eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/AggregateBasedConsistencyMarker.java:79-82` --
  `public AggregateBasedConsistencyMarker doLowerBound(AggregateBasedConsistencyMarker other) { throw new
  UnsupportedOperationException("Not implemented yet"); }`
* `eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/DefaultEventStoreTransaction.java:144-153` --
  `updateAppendPosition`, which calls `current.lowerBound(marker)` for every sourcing after the first
* `eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/DefaultEventStoreTransaction.java:129` -- the
  `onComplete` that calls it
* the same class's `doUpperBound` at `:84-92` is implemented, so the missing half is not a design decision about
  aggregate markers in general

=== What the reproduction observed

The existing integration-test suite, unchanged, run against PostgreSQL through the run-time backend selection. Of the 65
cases in the suite, three failed with this exception and no other cause:

* `MultiEntityCommandHandlingComponentSuiteIT.canCombineModelsInAnnotatedCommandHandlerViaStateManagerParameter`
* `MultiEntityCommandHandlingComponentSuiteIT.canCombineStatesInLambdaCommandHandlerViaStateManagerParameter`
* `CommandSequencingSuiteIT.concurrentEnrollmentsToSameCourseDoNotCauseOptimisticLockingFailures`, which reports it as
  `Expected no exceptions during concurrent enrollments, but got: java.lang.UnsupportedOperationException`

All three combine two entities in one command, which is what makes them source twice, and all three pass on the in-memory
store, whose marker implements `lowerBound`. The two multi-entity cases are the plainest statement of the blast radius:
combining two models in one handler is a documented, first-class thing to do, and it cannot be done on this store.

=== Why it matters

The exception names neither markers nor sourcing to the person who hits it, and it arrives from inside a command that did
nothing unusual. An application built and tested against the in-memory store will hit it the first time it runs against
the JPA engine, on any handler that sources twice -- which is most non-trivial ones.

=== Candidate fix

Implement it as the mirror of `doUpperBound`: take the lower sequence number per aggregate identifier, and the union of
the identifiers, so that an aggregate known to only one of the two markers keeps its position. If there is a reason the
lower bound of two aggregate markers is genuinely undefined, the throw should say that instead of "Not implemented yet",
and `DefaultEventStoreTransaction` should not reach it.

=== Reproduce

[source,bash]
----

    -Dtest=NoSuchUnitTest -Dsurefire.failIfNoSpecifiedTests=false -Dhunt.backend=postgres-jpa
----

The same command without `-Dhunt.backend` runs the identical classes against the in-memory store and is green, which is
the vector.

== F-16 -- An event skipped for ever because its own timestamp aged past the gap timeout

*Severity:* High +
*Status:* Open. Reproduced by test, on PostgreSQL, on both configuration paths. +
*Backend vector:* `in-memory: n/a` (no gaps to record -- an in-heap map has no index taken before a commit),
`hsqldb-tokens: n/a` (same event store), `postgres-jpa-chaos: FAIL`, `postgres-jpa-chaos-spring-defaults: FAIL`,
`postgres-jpa: intermittent`, `postgres-jpa-split-tokens: FAIL`.

The two `-chaos` arms hold a transaction open on purpose, so they reproduce it deliberately. The two arms that install no
fault at all reproduce it by accident, which is the more alarming half: `postgres-jpa-split-tokens` lost 2 and 4 committed
events on its two seeds of a clean engine, and `postgres-jpa` lost 0 on both seeds of one run and 2 on a seed of another.
Nothing forces the interval on those arms -- ordinary contention over a database is enough.

=== What is wrong

`AggregateBasedJpaEventStorageEngine` takes its `globalIndex` from a database sequence *before* the transaction commits,
so a reader routinely sees index `n+1` while `n` is a hole that will later fill. Recording that hole as a gap is what
makes the reader come back for it. Whether it records one is decided here:

[source,java]
----
// eventsourcing/src/main/java/org/axonframework/eventsourcing/eventstore/jpa/AggregateBasedJpaEventStorageEngine.java:427
boolean allowGaps = timestamp.isAfter(gapTimeoutThreshold);
return token == null
        ? GapAwareTrackingToken.newInstance(globalIndex, calculateGaps(globalIndex, allowGaps))
        : token.advanceTo(globalIndex, allowGaps ? maxGapOffset : 0);
----

`timestamp` is the **message's own** timestamp and `gapTimeoutThreshold` is `now - gapTimeout`
(`GapAwareTrackingTokenOperations.gapTimeoutThreshold()`). So an event that has aged past the threshold by the time a
reader first sees it advances the token to its index with a gap allowance of **zero**, and every lower index still
uncommitted at that instant is never recorded as a gap at all. When those transactions commit, the reader's token is
already past them and holds nothing that would bring it back.

The decisive point is that the ageing is not the *reader's* lateness. It is the interval between the event being created
in the handler and its transaction committing, and any of the ordinary reasons for that interval to be long -- a slow
store, a contended lock, a large transaction, a paused process -- is enough.

=== Evidence

Measured on the breakable PostgreSQL arm, with every commit held open between the rows being written and the transaction
committing, for twice the arm's gap timeout. The hold is what makes it reliable, not what makes it possible:

----
gap-core   readableEvents=88  deliveredEvents=85  stalled=true
  [NoCommittedEventGoesUndelivered] 3 committed event(s) never reached a consumer, for example
  [writer-3-4-w, writer-6-5-w, writer-6-10-w]; the read side had stopped accepting deliveries altogether,
  so nothing was in flight
gap-spring readableEvents=86  deliveredEvents=83  stalled=true
  [NoCommittedEventGoesUndelivered] 3 committed event(s) never reached a consumer, for example
  [writer-5-0-w, writer-5-0-d, writer-6-7-w]; the read side had stopped accepting deliveries altogether,
  so nothing was in flight
----

The events are in the store: the count they are missing from is a direct SQL scan of `aggregateevententry`, taken on a
connection of its own. The read side had stopped moving entirely for longer than the run's stall window, so nothing was
in flight, which is what makes this loss rather than lateness.

And on the arms that install no fault, at the framework's own 60-second gap timeout, on a clean engine:

----
MEASURED postgres-jpa-split-tokens seed 1 undelivered=2 decided=true caughtUp=false
MEASURED postgres-jpa-split-tokens seed 2 undelivered=4 decided=true caughtUp=false
MEASURED postgres-jpa              seed 1 undelivered=0 decided=false caughtUp=true
MEASURED postgres-jpa              seed 2 undelivered=0 decided=false caughtUp=true
----

Two things follow that the deliberate arms cannot establish on their own. The loss does not need a fault, and the events it
takes sit near the *start* of the store rather than the end -- in one history at store positions 47 and 50, committed at
2620ms, with the reader having delivered up to position 592 by 5592ms and then nothing for the following sixty seconds. It
is not a tail that ran out of time.

**What is not established is the mechanism at the default timeout.** The `allowGaps` comparison explains the compressed
arms exactly: a hold of twice the gap timeout guarantees the ageing. At sixty seconds it does not obviously apply to an
event committed 2.6 seconds into a run, and no attempt was made here to instrument the reader's token to find out which of
the gap machinery's several paths took it. The observation is reproducible and the mechanism at that timeout is open.

=== Both configuration paths, because they disagree

The two arms differ only in the gap settings, and the settings differ because the two configuration paths default them to
each other's values (finding F-1): the framework's own configuration record defaults `gapTimeout` to 60000ms and
`maxGapOffset` to 10000, and Spring Boot's autoconfigure defaults them to 10000ms and 60000. Both arms skip. So this is
not a consequence of one path's numbers; it is the mechanism, and the numbers only decide how long a transaction has to
be open before it bites -- ten seconds on a Spring Boot deployment and a minute on a plain one.

=== Why it matters

The loss is silent in every direction. The append succeeded and the caller was told so. The store holds the event and any
scan finds it. No error is logged, no token is refused, no exception reaches anybody. The only observable is that a
projection is permanently short of an event, discovered whenever somebody reconciles a read model against the store --
which for an event-sourced system is the one comparison that is supposed to be redundant.

=== How it was found

By holding a transaction open between the rows being written and the transaction committing, which is the only interval in
which the hole exists. Canary C7 -- forcing `allowGaps = false` in that same comparison -- turns the shared-resource arm
from `undelivered=0` on both seeds to `undelivered=3` and `undelivered=6`, which is the mutation reproducing a stronger
form of the same defect and is why C7 has stopped being useful as a *planted* defect. It took two attempts: the first delayed
`EventStorageEngine.AppendTransaction.commit()` and changed nothing at all, because on this engine that call does no work
and races the database transaction rather than preceding it (finding F-17).

It also needed the loss oracle to be able to decide. `DeliveryChecker` declined to call an event lost on a run whose read
side had not caught up -- correctly, because an interrupted run has lost nothing -- and a store that skips an index for
ever produces exactly that observation. The run now reports whether the read side had *stopped*, and loss is decided on a
stalled read side exactly as it is on one that caught up. That is the same guard that made canary C7 escape, closed.

=== Candidate fix

The comparison is between an event's own timestamp and the reader's clock, and those two are not commensurable: one is set
when the event is created and the other is read when the event is first seen, with an unbounded interval between them
that the framework does not control. Two candidates, neither free:

* compare against something the store assigns at commit time rather than against the message timestamp, so that the
  threshold measures how long the *index* has been outstanding rather than how old the payload is;
* or treat a hole below an aged event as a gap regardless, and rely on `gapCleaningThreshold` and `maxGapOffset` to bound
  the cost, accepting the read amplification the current comparison exists to avoid.

Whichever is chosen, the reference documentation for `gapTimeout` describes it as a performance setting for cleaning old
gaps and does not say that exceeding it can drop an event. That sentence is a fix in itself.

=== Reproduce

[source,bash]
----
./mvnw -Phunt -pl simulation -o test -Dhunt.excludedGroups=fuzz \
    -Dtest='StoreInfrastructureFailureTest$HoldingCommitsOpenPastTheStoresGapTimeout' \
    -Dsurefire.failIfNoSpecifiedTests=false
----

Needs Docker. The arm prints its own verdict vector and the count of events the store held that never reached a consumer.

== F-17 -- The database transaction's commit races the append transaction's commit

*Severity:* Medium +
*Status:* Open. Measured. +
*Backend vector:* `in-memory: n/a` (no database transaction -- the engine's own `commit()` is the commit),
`postgres-jpa: measured`, `postgres-jpa-chaos: measured`.

=== What is wrong

On a store whose transaction lives on the processing context, two separate actions land in the framework's `COMMIT`
phase, and the framework states plainly that it will not order them:

* the transaction manager registers its commit during `PRE_INVOCATION` --
  `TransactionManager.attachToProcessingLifecycle` does `processingLifecycle.runOnPreInvocation(pc -> { Transaction t =
  startTransaction(); pc.runOnCommit(p -> t.commit()); ... })`;
* the event store registers the append transaction's commit during `PREPARE_COMMIT` --
  `DefaultEventStoreTransaction.attachAppendEventsStep()` does `processingContext.onCommit(c -> tx.commit()...)` from
  inside its own prepare-commit action.

Both are `DefaultPhases.COMMIT`, and `ProcessingLifecycle`'s own Javadoc says that "actions registered in a `Phase` with
the same order may be executed in parallel"; `UnitOfWork` combines them with `CompletableFuture::allOf`.

So on such a store the events become durable and readable at a moment that has no defined relationship to
`AppendTransaction.commit()`. It may be before, during or after.

=== Evidence

From one run's history, for the first event delivered on the breakable PostgreSQL arm, with a two-second delay installed
after the rows were written:

----
event writer-3-0-w delivered at ms 615
  commit INVOKE ms 2492
  append OK   ms 2492
----

The event was handed to a consumer 1877ms before the append transaction's `commit()` was even entered. The engine's own
`commit()` is a documented no-op on this store -- "Transaction is in control of the entity manager executor, so do no
work here" -- so nothing was waiting for it.

=== Why it matters

Three consequences, and the third is the one that bites.

`AppendTransaction.commit()` cannot fail an append on such a store. By the time it runs, the events may already be
readable, so a failure there is a failure after the point of no return rather than a refusal.

`AppendTransaction.rollback()` cannot undo one either. The framework registers it through `onError` for any phase, and it
is already documented that a failure after the commit rolls back a batch that has been published (finding F-8) -- what is
new here is that the same is true for a failure *during* the commit phase, because the transaction may have gone first.

And the interface says none of this. `EventStorageEngine.AppendTransaction` reads as a two-phase protocol in which
`commit()` is the moment of durability, and for the in-heap engine it is; for a transaction-managed engine it is not, and
an implementer has no way to know which contract they are writing to. Every harness or interceptor that treats
`commit()` as the visibility point is wrong on half the stores -- which is exactly the bug this suite had, and is how
this was found.

=== How it was found

A fault was written to hold a transaction open by delaying `AppendTransaction.commit()`, on the reasonable assumption
that the transaction commits after it. The arm produced 154 `NoVisibilityBeforeCommit` violations and no skip at all,
which is the opposite of what it was built to find. Reading the delivery and commit timestamps out of the history showed
the delay was entirely after durability.

=== Candidate fix

Either give the two actions an order -- the storage engine's commit registered in a phase strictly before the transaction
manager's, so that `commit()` really is the last thing that can refuse an append -- or say in
`EventStorageEngine.AppendTransaction`'s Javadoc that on a store whose transaction is external, `commit()` is not the
durability point and must not be treated as one. The second is a documentation change and closes the trap for
implementers; the first closes it for callers as well.

=== Reproduce

[source,bash]
----
./mvnw -Phunt -pl simulation -o test -Dhunt.excludedGroups=fuzz \
    -Dtest='StoreInfrastructureFailureTest$HoldingCommitsOpenPastTheStoresGapTimeout' \
    -Dsurefire.failIfNoSpecifiedTests=false
----

Then read any history under `simulation/target/hunt-histories/gap-core-defaults/` and compare a `deliver` record's
`logicalTs` against the `commit` record carrying the same event identifier. The fault now delays
`StoreHook.afterAppend`, which is strictly before the transaction, so a current run shows the correct order; reverting
`LateCommitFault` to delay `onCommit` reproduces the measurement above.

== F-18 -- No reachable Axon Server connector links against this reactor

*Severity:* Blocking for coverage; not a framework defect. +
*Status:* Open. Measured. The Axon Server arm of the suite is blocked on it. +
*Backend vector:* `axonserver: BLOCKED`.

=== What is wrong

There is no Axon Server connector artefact that can be loaded against this tree.

* The in-tree `axon-server-connector/` directory does not exist, and the root POM's `<modules>` does not name it.
