01 · why

Why a second test suite?

Our normal tests
  • Check that a feature works: one input, one expected output
  • Run on one thread, with no failures happening
  • That is the happy path
This suite
  • Checks the framework's promises: "a conflicting write is rejected", "no committed event is lost"
  • While things go wrong: many threads, process crashes, network failures, slow databases
  • Because that is when production bugs actually happen

Extra problem: our CI re-runs a failing test up to 5 times before reporting it. A bug that only appears sometimes looks "flaky" and gets hidden. This suite never retries.

  • Concrete example to say: "A test that saves an event and reads it back passes. But what happens when two threads save at the same moment and the database connection drops mid-commit? No existing test asks that."
  • The retry point: retries exist to fight flakiness, but a real race condition also looks flaky. Retrying 5x buries it.
  • Keep this short - the interesting part is HOW you test failures reliably, which is next.
01 · concepts

The core idea: deterministic simulation testing (DST)

The problem with testing failures

Concurrency and failure bugs depend on timing. Run the same test twice, the threads run in a different order each time, the bug appears once in a thousand runs - and you cannot debug what you cannot repeat.

The DST answer

Take the randomness and the clock away from the operating system and put the test in charge of both. Then the same test run can be repeated exactly, as many times as you want.

How that is done

No real threads, no real clock. The simulator runs the "parallel" work itself, one small step at a time, and the seed decides whose turn is next: step of A, step of B, step of A... Same seed = same turns = same bug, every time.

seed - a starting number for a random generator. The same seed always produces the same sequence of "random" choices. So: same seed = same order of operations = same failures injected at the same moments = the same run, repeated exactly.
more seeds - each seed is one possible run: one ordering of steps, one timing of failures. Running 100 seeds tries 100 different runs. The rarer the bug, the more seeds it takes to hit it - so seed count is the search effort, and any seed that finds something is kept.
simulated time - the test owns the clock. Instead of waiting 60 real seconds for a timeout, the test moves the clock forward. Hours of timeout behaviour run in milliseconds.
  • This is THE foundational slide - go slow. Everybody must get "seed" before moving on.
  • Third box, in speech: "nothing in the test talks to the OS for time, randomness or scheduling - it all comes through objects we hand in. Hand in the same seed, get the same run."
  • Threads analogy: two threads racing = two people talking over each other; the OS decides who speaks when, differently every time. DST makes them take turns, and the seed is the list of turns. Replay the list, replay the exact conversation - including the moment it went wrong.
  • Seed analogy: a card deck. Shuffle normally: every game different. Shuffle with a seed: deal the exact same game again to study a bad hand.
  • Payoff: a bug found Tuesday replays Wednesday, on a colleague's laptop, in a debugger. Without DST, timing bugs are "could not reproduce".
  • Q: how can ONE thread test concurrency bugs? A: race bugs are caused by the ORDER of operations, not by physical parallelism. If some ordering breaks the code, the simulator can produce that ordering deliberately. One thread playing all parts can produce every ordering two real threads could.
  • Q: what bugs can it NOT find? A: ones needing true parallelism - CPU memory-model effects, missing volatile/synchronized at hardware level. For those we use Lincheck (own slide later) and real-thread runs. DST finds logic races; it is honest about the rest.
  • Q: how does time move without waiting? A: nothing sleeps. The scheduler keeps a list of "what happens when" and jumps the clock straight to the next event. That's why an hour of timeouts takes milliseconds - it's called discrete-event simulation.
  • Q: how does ONE number control a whole run? A: one random generator, seeded with it. Every decision - which task steps next, what data the workload sends, when a fault fires - is drawn from that generator. Same seed = same draws = same run.
  • Q: what if code reads the real clock or starts its own threads? A: then determinism breaks - that's the catch. It only works where clock/scheduling can be handed in from outside. Axon lets us inject the clock and executors; but the framework also starts some threads of its own, which we may not modify. That's why OUR determinism is partial (single-thread mode fully repeatable, real-thread mode not) - comes on the comparison slide.
  • Q: is this just property-based testing? A: related but no - property testing randomizes the INPUT DATA; DST also randomizes the SCHEDULE and the FAULTS. Same replay-from-seed idea, applied to time and order, not just values.
01 · concepts

Who invented this: FoundationDB

What they did (2010s, now Apple)
  • Ran their whole database cluster inside one process - fake network, fake disks, fake clock
  • Everything random came from one seed
  • Simulated years of cluster life, with constant injected failures, every night
BUGGIFY

Their production code contains lines like if (BUGGIFY) drop_this_message() - deliberate failure points, switched on only during tests. The database helps break itself where the developer knows it hurts most.

Result: bugs that would take years to hit in production were found in minutes of simulation - and every one could be replayed from its seed.

  • Say what a cluster-in-one-process buys: no real network or disks means the test controls every message and every write - so it can delay, drop or reorder any of them, on purpose, repeatably.
  • BUGGIFY in one sentence: "failure injection written by the same person who wrote the code, at the exact spot they were worried about."
  • Credibility note if asked: FoundationDB's testing reputation is why Apple bought them; the approach is now copied industry-wide.
01 · concepts

Who refined it: TigerBeetle

A financial database. Their simulator (they call it "VOPR") added two ideas we copied directly:

Idea 1 · reference model

Keep a tiny second implementation of the same rules - a few hundred lines, so simple it is obviously correct. Feed both the real database and the tiny model the same operations. If their answers ever differ, the real database has a bug.

Idea 2 · conservation law

Use a workload where one simple equation must always hold. For money: debits == credits, always. If any event is lost, doubled, or applied out of order, the equation breaks - without anyone writing a check for that specific bug.

  • Reference model analogy: checking a calculator against counting on your fingers - slow and simple, but you trust it.
  • Conservation law analogy: a cashier counts the till at closing. They don't know WHICH transaction went wrong - but they know SOMETHING did. Cheap to check, catches whole classes of mistakes.
  • Both ideas come back as concrete pieces of our suite in a few slides (DcbStoreModel, the Ledger).

*Why the differences: they built their products around the simulator. We test an existing JVM framework, and one of our rules is that we never change its code - so we trade some repeatability for testing against real infrastructure. To fully support it we would need the framework built for simulation: no thread it starts itself, every executor and clock handed in from outside, no hardcoded durations - every timing decision an injectable seam.

**Our workaround: the framework already accepts some parts from outside through its configuration - we hand it a fake clock and our own executors there. Everything else we control by wrapping: its store, its token store and its connections sit behind decorator classes we own, and the faults fire inside those wrappers. Framework code itself: untouched.

  • Row 1 (repeatable runs - partial*, the asterisk points at the footnote). Say: they wrote their products so that NOTHING talks to the OS - one scheduler they own runs everything, so a seed replays the entire run. Our yes is the single-thread mode: it replays the write side perfectly - same appends, same rejections, same order, every time. The scope: in multi-thread mode a seed does not replay the run (real JVM threads, OS scheduling; we may not rewrite the framework) - which is why multi-thread bugs are preserved as log files instead (row 2). And we know all this because we MEASURED it, we didn't guess. Follow-up "why not inject your own scheduler?": we inject everything the framework lets us (clock, executors); the threads it creates privately are out of reach without patching it.
  • Row 2 (replay a bug - all yes, different mechanism). They re-run from the seed and get the identical run. We save a log file (the "history") of everything that happened; re-checking the file gives the same verdict forever, on any machine. Follow-up "is that really replay?": it re-JUDGES, it does not re-EXECUTE - the evidence is preserved, not the execution. Follow-up "what if the bug is in something the log doesn't record?": the log records every operation at the framework's API boundary (append, commit, claim, delivery) - that boundary is exactly what the invariants are about.
  • Row 3 (simulated time - all yes). Same trick everywhere: the clock is an injected object, timeouts are shrunk. Our caveat if asked: a few framework durations are hardcoded and do not shrink - one of those became finding F-5.
  • Row 4 (BUGGIFY - partial*, same footnote). Their production code contains deliberate failure points ("if BUGGIFY, drop this message"), active only in tests. We have the same mechanism in the code WE own: wrapper classes around the framework (an event store wrapper that can vanish the next commit) and the workloads, placed at the commit and claim boundaries. One nuance if asked: framework code itself carries no such points (we never modify it, house rule), so a failure spot deep INSIDE a framework function is out of reach - ours sit at the boundaries around it.
  • Row 5 (reference model - FDB partial, TB and us yes). FDB mostly asserts properties per workload rather than keeping a full second implementation. TigerBeetle and we keep the tiny correct model and compare every operation's outcome against it. Follow-up "who checks YOUR model?": two things - planted bugs (canaries), and a cross-check against the TLA+ spec of the same rules: every one of the 960 cases in a small domain, both agree; and we first broke the cross-check on purpose to prove it CAN disagree.
  • Row 6 (conservation law - TB yes, us yes). TigerBeetle IS a ledger, so debits == credits is native for them. We chose a bank-ledger workload ON PURPOSE so the same cheap check exists here: balances must sum to the opening total. Follow-up "what about scenarios not about money?": the ledger is the default workload for every scenario, so the sum check rides along everywhere for free.
  • Row 7 (real infrastructure - only us). They never test against a real database because their product IS the database - simulation of their own disk and network is the whole story. Our system-under-test is framework x storage backend, so the real stores are part of what we test: real PostgreSQL and real Axon Server in Docker, network cut by a proxy, containers killed mid-write. Follow-up "why keep simulation then?": speed - simulation gives seconds-per-run feedback on every change; real-infra runs take tens of minutes and run nightly. Same checkers judge both, so results are comparable.
  • Row 8 (TLA+ - TB partial, us yes). TLA+ = describe a protocol as math, then a checker tries EVERY possible ordering of a small setup (own slide later). TigerBeetle's consensus protocol has a published formal spec, but it is not wired to their code - hence partial. Ours is wired: the invariant sentence in the model is word-for-word the sentence in the Java checker, and each real design bug has a model config that reproduces it plus one proving the fix. Follow-up "does TLA+ prove the code correct?": no - it proves the DESIGN correct at small size; the code is held to that design by the reference model and the identical wording.
  • Row 9 (canaries - they partial, us yes). Canary = plant a known bug, demand the suite goes red, revert (own slide later). Both companies do fault-model validation internally but publish nothing. We keep a public file (CANARIES.md) with every planted bug, what caught it - and the two that ESCAPED. Follow-up "why document the misses?": an escaped canary is a hole in a checker; hiding it would mean trusting a green run that hole flows through. Both escapes were later fixed and one led to a real finding.

02 · what we built

Three test levels, one shared judge

shared judge: the invariant list · the run log recorder · the checkers
Level 1 · simulation

One JVM, seeded

Real framework components (command bus, event store, processors) on a fake clock, with failure-injecting wrappers. Fast - runs on every change.

Level 2 · multi-node

A cluster in one JVM

Several framework instances share one store, like a real deployment. Lets us test node crashes, work stealing, clock differences - without Docker.

Level 3 · real infra

Real databases, real chaos

Real PostgreSQL and real Axon Server in Docker. We cut their network, kill processes mid-write. Slow - runs nightly/weekly.

oracle - the part of a test that decides pass or fail. A normal test's oracle is its assert line. Here the oracles are the checkers and the reference model - and they are the same at all three levels.
  • The point of the slide: levels differ only in HOW REAL the world is. The judging is identical - so a bug found in fast simulation is confirmed the same way against a real database.
  • Level trade-off in one line: L1 = seconds, every PR. L2 = distributed races, still no Docker. L3 = the truth, but tens of minutes.
  • Introduce "oracle" carefully - it comes up constantly from here on. It just means "the judge".
02 · what we built

How a test is put together

claimspromises the framework makes, collected from its docs and code. Numbered C1-C40. Plus M1-M18: questions the docs leave unanswered ("gaps").
invariantsrules that must hold on every run, e.g. "no event is delivered before its transaction commits". Each has a stable name and one exact sentence. 20 of them.
historythe log file of a run: every append, commit, claim and delivery, written as one JSON line each.
checkersprograms that read the history and report every invariant violation they find. All checkers run on every history, automatically.

Rule that keeps the suite honest: a test that cannot point to a claim number (C or M) does not get written.

  • Walk it top to bottom with ONE example thread: claim C1 says "an append that conflicts with a newer event is rejected" → invariant "every accepted append is also accepted by the reference model" → a run writes its history → the conformance checker replays it and flags any disagreement.
  • claim = a sentence from Javadoc/docs, with the file and line it came from. gap = a question the docs don't answer, e.g. "what happens to an event whose transaction commits after its slot timed out?" Nobody wrote that sentence - and that's where most of our real bugs came from.
  • A scenario here is a data record (workload + failures + seed), not code. The runner drives it, records the history, and the checkers judge afterwards. Tests don't judge themselves.
02 · what we built

Pass/fail is computed from the log file

The run produces the history; the checkers judge the history. So anyone can re-check a run later - no simulation needed, same verdict every time.

# a history file: line 1 describes the run, every other line is one operation {"scenario":"dcb_append_rejected_...","seed":42,"backend":"in-memory",...} {"type":"INVOKE","op":"append","id":"a-17","node":"n1","tags":["account:9"],...} {"type":"OK","id":"a-17","outcome":"ACCEPTED","position":381} # re-check a saved history from a run where the store's conflict check was broken on purpose: ./mvnw -Phunt -pl simulation -o test -Dtest=HistoryReplayTest \ -Dhunt.history=simulation/src/test/resources/hunt-histories/pinned-conflict-check-bypass.jsonl # prints: FAIL pinned_conflict_check_bypass - with every violation listed
  • Why this matters: multi-threaded runs are not repeatable from a seed (real threads). But the history file of what DID happen is saved - and re-judging that file works forever, on any machine. That is how a found bug is preserved as evidence.
  • Point at the two record types: INVOKE when an operation starts, OK/FAIL when it finishes. Two separate lines - so an operation that never finished (crash mid-write) is representable. That detail matters a lot later.
  • Good first-day exercise: run this exact command. It needs no Docker and takes seconds.
02 · what we built

Our reference model: DcbStoreModel

What it is
  • ~300 lines of plain Java - the event store's append rules, written as simply as possible
  • Every history is replayed through it
  • Wherever the real store's answer differs from the model's, that is a bug - and the model names which rule was broken
Why not just write more asserts?
  • Hand-written checks only catch what somebody thought of in advance
  • A model catches any deviation from the rules, including ones nobody imagined
  • How: both get the same operations, both answer. Model says "reject", store said "accept"? Bug found.
  • Same idea as TigerBeetle's - slide 5, idea 1

DCB = Dynamic Consistency Boundary, the framework's optimistic-concurrency protocol: an append says "reject me if a conflicting event was stored after point X". The model encodes exactly when a store must accept or reject.

  • Give the DCB one-liner slowly for people who don't know it - "compare-and-swap for event streams" lands well with juniors.
  • The model is deliberately sequential and dependency-free, so it stays obviously correct - the whole point is that we trust it more than the real thing.
  • We also cross-checked the model against a formal specification of the same rules: all 960 possible cases of a small domain, both agree. And we broke the cross-check on purpose first, to prove it CAN disagree - a comparison that can't fail proves nothing. That habit repeats through the whole suite.

02 · what we built

The Ledger workload: money as a bug detector

The idea, in three steps
  • Every test needs traffic to push through the framework: commands in, events out, a read model. That traffic is called the workload
  • The traffic could be anything - we made it bank accounts and transfers
  • Why: money cannot appear or disappear. If the balances don't add up at the end of a run, the framework broke something - whatever the test was actually about
What a broken sum reveals
  • money vanished → an event was lost
  • money duplicated → an event was processed twice
  • an overdraft appeared → a forbidden write got through
  • books disagree with the events → the read model is corrupted

This is slide 5's idea 2 in practice: one free bug detector, running inside every test, catching mistakes nobody wrote a check for.

  • The story of this slide in one sentence: "our tests don't push random noise through the framework - they push money, because money is self-auditing."
  • Walk it as cause and effect: a test about, say, node crashes runs its crashes - and meanwhile the transfers flow. At the end we count the money. Books balance = nothing was lost, doubled or corrupted along the way. Books off = a bug, even though the crash-test itself passed its own checks.
  • Cashier analogy: the cashier counts the till at closing. They don't know WHICH transaction went wrong - they know SOMETHING did. Cheap check, catches whole classes of mistakes.
  • Proof it works: during canary campaigns, a deliberately planted double-processing bug was caught by the sum check alone - nobody had written an assertion for it. Happened twice, in two separate campaigns.
  • Right card mapping if asked: each money symptom is one framework failure - lost event, duplicate processing, bypassed conflict check, corrupted projection.

Terminology

  • claim vs invariant: a claim is what the framework promises; an invariant is what the suite checks. One invariant can cover several claims.
  • checker vs oracle: every checker is an oracle, but not every oracle is a checker (the model and the sum check are oracles too).

02 · vocabulary II

Terminology II

verdictPASS / FAIL / INCONCLUSIVE. The third value means "this run cannot tell" - and it is never rounded up to PASS.
faultA failure we inject on purpose: dropped commit, cut network, killed process, jumped clock. Industry also says "nemesis" - same thing.
landing evidenceProof the injected fault really happened, taken from the affected thing itself (e.g. the container's exit code). No proof = INCONCLUSIVE.
canaryA bug we plant in framework code on purpose, to prove the suite notices. Applied, measured, reverted. A check that never caught a planted bug cannot be trusted.
verdict vectorThe per-store row of verdicts from slide 11. Tells you whose bug it is.
tierHow hard a run pushes: SMOKE (one fault, every change) → HARDENING (fault pairs) → RELEASE (fault storms).
scenarioOne test's declaration: workload + faults + store + timescale + seed. It is data - adding a scenario changes no harness code.
expected-gap testA test that passes while a known bug exists and turns red when the bug is fixed. How we track a bug without fixing the framework ourselves.
  • Spend time on INCONCLUSIVE: a distributed operation has three outcomes (worked / failed / unknown - e.g. timeout: did the write land?). A test of such a system inherits all three. Collapsing "unknown" into pass or fail is lying.
  • And on expected-gap test: sounds backwards, is very practical - the suite documents today's broken behaviour, and the moment someone fixes the framework, the test flips and tells us to update the books.
  • Canary gets its own slide later - just plant the word now.

03 · tools

TLA+ - checking the design itself

What it is

A language for describing a protocol as math (by Leslie Lamport). Its checker, TLC, then tries every possible ordering of events in a small setup - not a sample of orderings, all of them.

Who uses it

Amazon used it on S3 and DynamoDB and found design bugs that needed 35 steps to trigger - no test would ever stumble on that. Also Microsoft, MongoDB, CockroachDB.

How we use it

Two small models: the append protocol and the token-claim protocol. Each real design bug we found has a config that reproduces it in the model and a second config proving the proposed fix removes it. One TLC run takes about a second.

how it works - no magic math: you describe the system as a state (the value of every variable) and the moves allowed from each state ("a writer may append", "the store may reject"). TLC starts at the initial state and mechanically visits every state any sequence of moves can reach - like walking every path in a maze - checking the invariant at each one. A small setup has a finite number of states, so a computer really can visit them all.
why both TLA+ and simulation? Simulation samples some orderings of a big real system. TLC tries all orderings of a small abstract one. Different nets - together they catch more.
  • Demystify - it's not academic decoration: finding F-14 (a store rejecting appends it must never reject) reproduces in TLC before any database container even starts.
  • The invariant sentence in the model is word-for-word the same as in the Java checker (the MachineName rule from vocabulary) - one property, two checkers, zero drift.
  • Bounds honesty: TLC proves things only for the small setup you give it (e.g. 2 writers, 3 events) - that's usually where protocol bugs live anyway.
  • Q: what does a "state" actually contain? A: a snapshot of every variable in the model - which events are stored, where each writer's consistency marker points, who holds which claim. Two states differ if any variable differs.
  • Q: what does the spec look like? A: a short file (ours are one-two hundred lines) with three parts: the variables, the starting state, and the allowed moves written as before/after rules. Readable with basic set notation - no advanced math needed.
  • Q: how many states does it visit, how long? A: thousands to a few million for our setups - about a second per run. This is also the limit: add more writers/events and the state count explodes. That's WHY the setup stays small.
  • Q: what happens when it finds a violation? A: TLC prints the exact path - step 1, step 2, ... - from the start to the broken state. That trace IS the bug reproduction at design level: you read exactly which sequence of moves breaks the rule.
  • Q: why believe results at 2 writers and 3 events? A: experience ("small-scope hypothesis"): protocol bugs almost always show up with very few actors - you need two writers for a race, not twenty. It's evidence, not absolute proof; the suite's runtime checks cover the large sizes.
  • Q: the model isn't the Java code - what connects them? A: two bridges. The invariant sentence is word-for-word identical in both. And our executable reference model (slide 10) was cross-checked against the TLA+ spec: all 960 cases of a small domain, both give the same answer.
  • Q: what's a "violated/fixed pair"? A: two configurations of the same model. One encodes today's flawed behaviour - TLC finds the violation, matching the real finding. The other encodes the proposed fix - TLC finds nothing. Together they say: we understand the bug AND the fix closes it, before anyone writes framework code.
  • Q: can I run it? A: yes - formal/tla/README.md has every command and every result; the tool is one downloadable jar, each run about a second, no Docker.
  • Q: does it check performance or timing? A: no - only ordering and logic. Time, latency and load are the simulation's and the real-infra tier's job.
03 · tools

Time compression - bugs live in ratios

The idea

Timeout bugs don't care about absolute durations - they care about ratios: a batch that takes longer than the claim timeout, a transaction that outlives the gap timeout, a pause longer than the extension interval. Shrink all the timeouts to milliseconds and the same races happen in seconds instead of hours.

How we use it

Every timeout-related scenario runs with compressed timeouts by default (HuntTimescale), plus a realistic-timeout variant at night. The clock and the executors are injected, so the harness controls them.

  • Concrete example: the gap timeout is 60s by default. Instead of a 2-minute test holding a transaction open, we set it to 50ms and cross it on purpose in milliseconds.
  • Honesty point, worth saying explicitly: repeatability was MEASURED, not assumed. Single-thread mode: same seed = identical run. Real threads: nothing repeats - which is why the log file, not the seed, is the evidence.

Fault injection - breaking things on purpose

Our faults (each is one small class)
  • store: vanish the next commit, duplicate it, add latency, reject it
  • tokens: deny a claim, make the token store time out
  • node: crash it, pause it (like a long GC), jump its clock
  • infra (level 3): cut the network, kill -9 a container

Gentle first, on purpose: when a one-fault run fails, you know exactly which fault caused it.

  • Landing evidence example: we don't trust "I called the kill command" - we read the container's own exit code. Intent is not effect.
  • The pause fault exists for a specific production bug class: a long GC pause makes a node lose its work claim while it is mid-batch; the "zombie" wakes up and writes anyway. kill -9 can never produce that - only pause can.
03 · tools

Lincheck - brute-forcing thread orderings

What it is

A JetBrains library. Give it one class and a few operations; it runs them on parallel threads in many different orders and checks every outcome can be explained by SOME sequential order of the calls.

Who uses it

JetBrains on Kotlin coroutines; it has found real bugs in the JDK's own concurrent collections.

How we use it

On the small concurrent building blocks in isolation: the in-memory token store and the in-memory event store's append path.

division of labour - Lincheck hammers one data structure with thousands of orderings; the simulation drives realistic whole-system flows. A race that needs a very specific thread order is Lincheck's job; a race that needs a crash plus a timeout is the simulation's.
  • Plain definition of the property it checks (linearizability): "the concurrent execution gave results as if the calls had run one at a time in some order". If no such order exists, something is broken.
  • Keep this slide quick - it's a supporting tool, not a pillar.
  • Q: how does it work, step by step? A: you mark the operations of one class (store token, fetch token, claim). Lincheck then invents little test programs: "thread A does these two calls, thread B does these two" - runs each many times on real parallel threads, records the results, and checks: is there ANY one-at-a-time order of those calls that produces these results? No such order = bug, and it prints the exact program that broke.
  • Q: how is that different from our simulation? A: opposite trade-offs. The simulation runs the WHOLE framework with faults and timeouts, but samples orders. Lincheck takes ONE small class, no faults, and hammers the orders themselves - including effects only real parallel threads produce (two CPUs seeing stale values of the same field). Deep-and-narrow vs wide-and-realistic.
  • Q: what does a failure look like? A: a printout: the two thread programs, the actual results, and the verdict that no sequential order explains them. Copy-pasteable into a bug report.
  • Q: why only the in-memory token store and event store paths? A: Lincheck is for single-JVM data structures. Anything that talks to a database is dominated by slow, nondeterministic IO - wrong tool there; that's what level 3 is for.
  • Q: where does it run? A: inside the default hunt build with a bounded number of test programs, so the fast tier stays fast; the nightly fuzz tier raises the count.
  • Q: has it found anything? A: it is the regression net at the lowest level - what each arm has produced is recorded in FINDINGS.adoc; point them there rather than quoting from memory.
03 · tools

Real infrastructure: Testcontainers + Toxiproxy

What they are

Testcontainers: starts real services (PostgreSQL, Axon Server) as throwaway Docker containers from inside a JUnit test. Toxiproxy: a small proxy you put between app and database - then you can cut, delay or throttle that connection from test code.

Why we need them

Simulation proves the logic. Only a real database proves data survives a real kill -9, and only a real network connection can half-die the way production networks do.

How we use them

Level 3 runs real postgres:16 and real Axon Server. All traffic goes through Toxiproxy. Scenarios cut the wire mid-commit, kill containers mid-batch, and hold transactions open past the store's gap timeout.

Bonus: our pre-existing integration tests can now run unchanged against a real store with one flag: -Dhunt.backend=postgres-jpa.

  • Explain the nastiest network failure in words: "half-open" - the connection looks alive but data never arrives. Much more production-realistic than a clean disconnect, and Toxiproxy does it on demand.
  • War story (short): the Axon Server test arm was believed "blocked" for a whole phase - the released connector was missing one method the compiler couldn't see missing (AbstractMethodError at runtime). Now a compatibility check runs in the default build and names exactly which methods a connector version lacks.
  • The one-flag multiplication is a big practical win - years of existing tests suddenly run against real PostgreSQL.
03 · tools

Jepsen's playbook - learning from broken databases

What it is

Jepsen is a famous testing project (Kyle Kingsbury) that broke nearly every major database: run concurrent clients, inject failures, record every operation, analyse the log afterwards. Sound familiar? Our history-and-checkers design follows it.

The pitfall catalogue

A distilled list of HOW systems actually failed across all those tests: lost acknowledgements, stale reads, membership races, clock skew, lease expiry, sequence gaps...

How we use it

We walked all 16 catalogue entries against Axon's claims and asked "could this happen here?" - that produced 13 concrete failure hypotheses, which became scenarios. It is also the recipe for covering any new subsystem.

  • One walk example end-to-end: catalogue entry "sequence gaps" → hypothesis "a JPA sequence gap is given up after its timeout while a slow transaction commits later - is that event ever delivered?" → scenario → real finding F-16 (it is not delivered). Full story in a few slides.
  • Point: you don't need to be creative about failure modes - the industry already paid for this list. Walk it.
  • If asked about Elle (Jepsen's analysis tool): our log format is deliberately convertible to its input format, but we haven't needed it yet.

Canaries - testing the tests

The loop
  • Plant a known bug in framework code (e.g. weaken the conflict check)
  • Run the suite - it must go red
  • Revert the bug; write down what happened either way
Why bother
  • A check that never caught a planted bug might catch nothing - green would be meaningless
  • Two of our canaries escaped (the suite stayed green). Both write-ups are kept - each escape exposed a real hole in a checker
  • formal/CANARIES.md also lists what has never had a bug planted at it
  • This is why anyone should trust a green run from this suite: its checks have demonstrably gone red on planted defects.
  • Escape 1, the full story: we planted a lost-event bug, and the suite stayed green. Why: the delivery checker refused to judge any run whose read side had not fully caught up - and a store that skips an event forever leaves the read side permanently behind, so the checker politely declined to look at exactly the runs containing the bug. The fix: the checker now also decides when the read side has STOPPED moving. That widened rule is the one that later caught real finding F-16 (the committed-but-never-delivered event). The hole in the checker was hiding a real bug class - that's why escapes are more valuable than catches.
  • Escape 2, the full story: on the Axon Server arm, a planted bug pushed the arm into INCONCLUSIVE instead of FAIL - undecided is not red, so the canary escaped. The arm's checks HAVE gone red on two real defects there (worth more than a planted one), but that is not the same proof. CANARIES.md records the escape and the few lines that would close it.
  • Why keep escapes in the file: overwriting an escape with its later fix would erase the evidence that the hole existed - and the hole is the finding. Next reader must be able to see what the suite could NOT catch and when that changed.
  • The "never canaried" list: CANARIES.md honestly names what has never had a bug planted at it: the split/merge logic, the sequencing-policy path, and every tier above smoke. Meaning: nobody KNOWS whether those checks can fail. Until a bug is planted there, green in those areas is hope, not proof. It's also a perfect self-contained first task for someone new: the recipe is four commands, the result is a row in CANARIES.md either way.

Finding the claims in the first place

What claims mining is

Reading the framework's Javadoc, reference docs and code, and writing every promise down as one testable sentence with its source location - plus every question the docs leave open.

Help: the knowledge graph

A prebuilt, queryable graph of the codebase (graphify) answers "what touches the TokenStore?" in seconds. Used for orientation only - the source code is always the authority.

The result

40 claims (C1-C40) and 18 gaps (M1-M18). Each claim carries a confidence: stated in the docs, or only visible in the code - and a promise that exists only in code is itself a documentation bug.

Two rules: a claim the code contradicts is written up as refuted (a result, not a failure), and the list is never padded to look bigger.

  • Example claim to read out: C1 - "an append whose condition conflicts with an event stored after its marker is rejected", anchored to the exact file and line in the engine.
  • Example gap: M3 - "no documented limit on clock difference between nodes for claim stealing". That silence became a scenario and then finding F-10.
  • This step is why every test traces to a number - the numbering isn't bureaucracy, it's the audit trail from doc sentence to test.

04 · how it hunts

From docs to bug: the pipeline

mine claimsread docs + code → promises (C) and unanswered questions (M)
walk pitfallscheck each known failure pattern against the claims → hypotheses
write a scenariofive required fields: what is checked · what load · proof faults fired · how unknowns count · how long it runs
pick invariantsreuse existing rules, or add a new one to the registry
plant a canaryprove the new check can actually fail
record the restwhat stays untested is written down, with an owner
  • The pipeline is the reusable part - it's how a subsystem with zero coverage today (queries, dead-letter queues) gets covered tomorrow with the same rigour.
  • The five scenario fields each block a classic mistake: no defined check = a load generator pretending to be a test; no fault proof = green under a fault that never fired; no unknown-handling = timeouts silently counted as passes; no run budget = quoting a strong verdict from a weak run.

Most findings came from the gaps, not the claims

StepThe chain that produced finding F-16
pitfallknown pattern: "sequence gaps in a store that assigns numbers before commit"
gap M2docs say a gap that stays empty too long is dropped for performance. Nothing says what happens if the slow transaction commits after that.
scenariohold a transaction open past the gap timeout on real PostgreSQL, then commit it
finding F-16the committed event is never delivered. On both configuration paths.

Same pattern for F-9 and F-10. Documented promises usually got tested by their author. The unanswered questions were tested by nobody - so that is where we dig.

  • Walk the four rows slowly - this is the method paying off end to end, from reading docs to a serious bug on a real database.
  • Spell out the finding for a junior: an event was successfully committed, the store acknowledged it, and consumers will never see it. Silent data loss of a committed event.
  • Status honesty: WHY it happens on a clean engine isn't fully explained yet - one of the two most valuable open questions in the suite.
04 · how it hunts

When a run goes red: the five steps

1 · huntrun a tier, or point an existing scenario at another store. Never change framework code (suite rule).
2 · triagealready known in FINDINGS.adoc? And suspect the test harness before the framework - the first red run of every new test arm has usually been a harness bug
3 · reproduceget the per-store verdict vector, and keep the run's history file - the file is the evidence, because multi-threaded runs cannot be replayed from a seed
4 · verifythink you found the cause? Break that exact thing on purpose and confirm the verdict moves. If it doesn't, your explanation is wrong.
5 · pin or rejectpin: a findings entry + a proposed fix + an expected-gap test + the history file. Reject: write down what it really was; if the harness was wrong, fix the harness
  • Same five steps whether a human or an AI agent does the hunting - the full version with the details lives in the axon-hunt skill (references/hunting-loop.md).
  • Step 2 humility is earned: in one phase, four separate harness bugs produced convincing-looking "findings". Assume the harness first.
  • Step 4 is the one people skip. A theory that hasn't moved a verdict is just a theory.
04 · how it hunts

What gets reported to the framework team

The bar: a test that fails on current code and passes once fixed. Nothing weaker gets filed as an issue.

Kind of findingRecorded in FINDINGS.adocFiled upstream
Behaviour wrong, a failing test proves ityesyes
Behaviour wrong, but no test can be made to failyesno
Docs wrong or silent, behaviour fineyesno
A design we would prefer differentlyyesno
Bug in our own harnessyes, and fix itno

Why: a maintainer can act on a failing test immediately. A grep or an argument costs them the same triage with no proof. Recording internally and reporting upstream are two different bars.

  • Also worth saying: nobody forces a test into existence to meet the bar - a fake that asserts against itself proves nothing. A finding honestly recorded and not filed is a fine outcome.
  • FINDINGS.adoc takes everything the suite learned; GitHub gets only the provable subset.

Adding your own - everything is a plug-in

To add a…You write
invariant + checkerone registry row + one Checker class + one registration line + a planted bug proving it can fail
faultone Fault class + a test proving it fires
workloadone Workload class
store backendone HuntBackend class + one registration line - every existing scenario then runs against it
canarya planted bug, measured, reverted - only the write-up stays
TLA+ modela .tla file + a broken config and a fixed config

None of these edits an existing class. And a rule to remember: a new property is finished only when the same sentence exists in three places - the registry, the checker, and a scenario that exercises it.

  • Why the plug-in shape matters, with the war story: the first attempt at running tests per store wrote 19 new classes per store. Deleted, redesigned to runtime selection: one class per store, total. If adding something means editing existing classes, the design is wrong - fix the design.
  • Step-by-step recipes: formal/INVARIANTS.md sections 5-6.
  • Three-places rule guards against a property nobody checks, or a check nobody can find.

What it does not cover yet

Known limits of current runs
  • Most arms run few seeds, at the light (smoke) tier
  • One cluster size per test - a bug needing 5 nodes won't show at 4
  • The pause fault exists but no scenario uses it yet
  • Exactly-once delivery never tested end-to-end (needs a transactional read model we don't have)
Remains to be tested
  • Queries and subscription queries
  • Dead-letter queues, sagas (not in this codebase version)
  • Schema evolution, upgrades, XA transactions
  • Axon Server clustering
  • Two findings with unexplained causes: F-16, F-19

All written down per test arm in formal/HUNT-NOTES.md, with owners. A suite that can't say what it doesn't cover can't be trusted about what it does.

  • Present this as strength, not confession - the honest ledger of limits is what makes the green runs meaningful.
