= Vertical Slices
:navtitle: Vertical slices
:reftext: Vertical slices

The other approaches keep the process in one class. This one asks whether it needs to be a thing at all.

Often the answer is no. What looks like a saga is a handful of independent reactions, each of the form "when this
happens, do that". In Vertical Slice Architecture each is a folder, and nothing outside it needs to know it exists. If
you model with Event Modelling you will recognise these as automation slices, drawn between an event and the command it
triggers, so this page treats the two as mostly the same thing.

== When to use it

Use this if you already structure your application in vertical slices, or if you model with Event Modelling and the
process appears on the model as a series of automations rather than as one box.

It is also the approach with the best transactional profile, so it is worth considering even when the process does feel
like one thing.

[TIP]
====
Where xref::workflows.adoc[[.advanced-framework]#Workflows#] are available to you they remain the recommended answer, whatever
the process looks like. This page is what to write when they are not.

Among the approaches that are, start here for new processes. A process class is easy to introduce later if you find you
need one, whereas a process class written up front tends to accumulate responsibilities that were never really shared.
====

There is no check for whether payment was already asked for. There is nowhere to check, and no need: the reference is
derived from the rental, and the payment side refuses to prepare a second payment under a reference it already
knows. Idempotency lives where the decision lives.

That leaves the processor's tracking token as the entire to-do list. Everything before it has been done, everything
after it has not, and a redelivery is harmless. No state object, no schema, no cleanup.

[NOTE]
.Slices do not share lookups
====
If three slices need the same lookup, each keeps its own. That duplication is deliberate: slices are independent, and
a shared lookup couples them, so a change made for one slice can break another. If the duplication becomes genuinely
painful, that is a signal the slices are really one thing, and a process class may be the better shape after all.
====

[#state-per-slice]
== Each slice chooses its own state

The lookup above is one answer to "where does this slice get what it needs". It is not the only one, and the choice is
made per slice rather than once for the whole process. That is the practical difference between this approach and a
process class: there, one decision covers every reaction; here, each slice answers only for itself.

All three approaches from the rest of this guide are available inside a slice:

[cols="1,2,1",options="header"]
|===
| Inside a slice | Reach for it when | Works across

| xref::state-in-a-repository.adoc[A repository]
| The slice needs to remember something nothing else records, or you want its progress to be queryable.
| Any number of event store contexts

| xref::state-from-context-events.adoc[Context events]
| What the slice needs is already implied by events in the same event store context. The lookup above is exactly this.
| One event store context only

| xref::state-from-process-events.adoc[Process events]
| The slice must record something of its own, typically because the other side's events are out of reach.
| Any number of event store contexts
|===

The last column counts event store contexts, not bounded contexts, and it is the constraint an entity brings with it:
a slice that injects one is sourcing from a single context, because no `EventCriteria` spans two.

A process usually ends up mixing them, and choosing per slice is the advantage. In the rental example most slices need
nothing, three read a lookup from context events, and none needs a repository. Had the payment side sat in a different
Axon Server context, or been a third-party provider whose events never reached this application, those three would
have had to record their own instead, and only those three. Nothing else about the process would change.

[TIP]
====
Slices choosing differently is not inconsistency. A slice that needs a queryable record and one that needs a two-field
lookup have different requirements, and making them share an answer is what produces the coupling this approach exists
to avoid.
====

== The whole process

The rental payment process decomposes into six slices, and the split between stateless and not is the interesting
part:

[cols="2,1,1",options="header"]
|===
| Slice | Triggered by | State

| When bike requested, then prepare payment | `BikeRequested` | none
| When request rejected, then cancel payment | `RequestRejected` | none
| When payment confirmed, then approve request | `PaymentConfirmed` | lookup
| When payment rejected, then reject request | `PaymentRejected` | lookup
| When payment cancelled, then reject request | `PaymentCancelled` | lookup
| When cancel rental payment, then cancel payment | `CancelRentalPayment` command | none
|===

The rental-triggered slices are stateless because the trigger event carries everything the command needs. The
payment-triggered ones are not, because a payment event knows only the reference.

The last slice is stateless for a different and more interesting reason. It could check whether cancelling is still
worthwhile before passing the request on, and deliberately does not: that is a question about the payment, the payment
side answers it authoritatively, and a check here could only ever be a stale copy of that answer. Duplicating a
decision that is not yours to make adds no safety and can add confusion.

== Compensation

Nothing in this arrangement notices when a rental is rejected for reasons of its own, unless a slice says so. Without
"when request rejected, then cancel payment", a rental turned down on other grounds leaves a payment outstanding
forever.

Cleanup like this is easy to leave implicit, buried in whatever code decides the process is over. Here it is a slice
like any other, which makes it visible on the model and testable on its own.

== Trade-offs

|===
| Good | Not so good

a|
* The best transactional profile: every slice does exactly one thing.
* Most slices need no state at all.
* Nothing to end, because nothing was ever running.
* Slices are independently testable, deployable and deletable.

a|
* No single place describes the process. Only an event model shows it whole.
* A reader has to find six files to understand one flow.
* Duplication between slices that need the same lookup.
|===

That first drawback is the real one. If the process is something people reason about as a unit, discuss as a unit, and
draw on a whiteboard as a unit, then scattering it across six files hides something important. If it is really a set of
independent rules that happen to concern the same identifier, this arrangement tells the truth and a process class does
not.

It is worth taking "only an event model shows it whole" literally rather than as a figure of speech. The
xref::bike-rental-event-model.adoc[bike rental event model] is that whole view: every slice on this page is one purple
sticky on it, and the flow they add up to exists nowhere else. If your team keeps such a model, this drawback is largely
paid for already. If it does not, the six files really are the only description there is.
