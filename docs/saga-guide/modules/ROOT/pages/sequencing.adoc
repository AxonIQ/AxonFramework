= Sequencing
:navtitle: Sequencing
:reftext: Sequencing

A pooled streaming event processor handles many processes concurrently. Events belonging to *one* process must still
be handled in order, or a `PaymentPrepared` can still be in flight while the `PaymentConfirmed` that supersedes it is
already being processed. Sequencing is how a process keeps its own events ordered while different instances run in
parallel.

The framework groups events with a `SequencingPolicy`: two events that resolve to the same sequence identifier are
handled one after the other, and events that resolve to different identifiers may run concurrently. A process therefore
wants every event about the same instance to resolve to the same identifier, and events about different instances to
resolve to different ones. For the general behaviour, defaults and the throughput trade-off, see
xref:{page-component-version}@axon-framework-reference:events:event-processors/streaming.adoc#sequential_processing[sequential processing]
in the reference guide.

`PropertySequencingPolicy` reads the named property off each event, so it fits any component whose events agree on what
that property is called. A vertical slice handles a single event type, so its own event always carries the property and
the built-in policy is all it needs.

== Two bounded contexts that name the correlation differently

A single process class that handles events from both sides has the harder case. One side calls the correlation
`rentalId` and the other `paymentReference`, so no single `PropertySequencingPolicy` spans them: a policy keyed on
either name leaves the other side unsequenced. Write a policy that routes on the message's `QualifiedName` and
delegates to a typed policy per event type. The example module contains one.

[WARNING]
====
Two mistakes in such a policy are easy to make and hard to see.

Extract the *raw* correlation value, not a typed wrapper. Returning `RentalId` from one side and `PaymentReference`
from the other means the two never compare equal, so the two sides land in separate sequences and the policy silently
does nothing.

Target *concrete* payload types, never a shared supertype. Converting to an interface works in memory, where the
payload is already an object, and fails against a real event store, where it arrives as bytes no converter can turn
into an interface. A test using plain objects will not catch this.
====

== Where next

Sequencing keeps one process's events ordered; it does not make the commands a process sends safe to receive twice.
That is a separate rule, covered under xref::index.adoc#two-rules[the two rules that apply to every approach]. If you
are migrating an Axon Framework 4 policy, the
xref:{page-component-version}@axon-framework-reference:migration:paths/sequencing-policies.adoc[sequencing policy
migration path] maps the old API to the new one.
