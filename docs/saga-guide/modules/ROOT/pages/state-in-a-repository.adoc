= State in a Repository
:navtitle: State in a repository
:reftext: State in a repository

The process keeps what it needs to remember in a table of its own. It is the most familiar of the approaches and the
right place to start if you are unsure.

The state is an ordinary record with ordinary columns, which is the whole point: you can query it, index it, report on
it, and join it. A process whose progress somebody will eventually ask about wants exactly that.

== When to use it

Use this when the process genuinely has to remember something, and either you want that memory queryable or the events
it reacts to are not all in an event store you own.

It asks nothing of the events it reacts to, which is what sets it apart. If the payment side is a third-party provider
whose events you merely receive, this still works, where
xref::state-from-domain-events.adoc[deriving state from domain events] cannot. What it does ask for is a place to
write and a transaction manager, for the reason below.

There is no ceremony here, and the absence is worth explaining, because storing process state alongside a tracking
token looks like it should need some.

One thing the sample leaves out for brevity: this class handles events from both contexts, which name their
correlation differently, so it needs a sequencing policy that spans them. See
xref::index.adoc#sequencing[sequencing] in the overview.

[#transaction]
== Where the transaction comes from

Nowhere in this class, which is the point. With a `PlatformTransactionManager` on the classpath, Axon Framework wraps
each unit of work in a transaction that opens before the handler is invoked and commits alongside the tracking token.
It also requires the phases to run on one thread, so the handler body executes on the thread that transaction is bound
to.

The write above therefore lands in that transaction without asking. The row and the token commit together, or neither
does. No `@Transactional`, no `runOnPrepareCommit`, no callback.

[#ordering]
== Why the write comes first

Purely so that it happens on the handler's own thread, where the transaction is bound. Ordering carries no correctness
weight here, because a failed command takes the write with it: the handler fails, the transaction rolls back, the row
is gone as though it had never been written, and the tracking token stays put so the event is redelivered. The
redelivery finds no row, so the guard lets it through and the process tries again from the top.

What does break is deferring the write until after the command has answered:

[source,java]
----
// Do not do this
return dispatcher.send(command)
                 .getResultMessage()
                 .thenRun(() -> repository.save(state));
----

That callback runs on whichever thread completed the command's future, where nothing is bound, so the write escapes
the transaction that commits the token. Recovering from that costs a hop back into a unit-of-work phase to find a
transaction again, and writing first removes the callback and the hop together.

[NOTE]
====
One kind of process has no choice but to defer: one that cannot know what to store until the command has answered. If
`PreparePayment` returned a generated payment identifier the process had to keep, the write could not precede the
dispatch, and it would have to be registered on the processing context to stay inside the transaction:

[source,java]
----
return dispatcher.send(command)
                 .getResultMessage()
                 .thenRun(() -> context.runOnPrepareCommit(ignored -> repository.save(state)));
----

Deriving the payment reference from the rental identifier is what buys this process its way out. It is another reason
to check whether the correlation is derivable before deciding where state lives.
====

Whichever shape you end up with, the property to preserve is that the state and the token commit together. A process
whose state can commit without its token, or the reverse, will drift, and the drift only shows up under failure.

[#ending]
== Ending the process

Deleting the row is the simplest way to end, and it is what the sample does. It is safe here for a specific reason:
every command this process sends is idempotent, so a redelivery arriving after the row is gone restarts the process,
re-dispatches, and the receiving context declines to append anything.

If that were not true, deleting would be unsafe, and you would keep a tombstone row instead:

[source,java]
----
process.markCompleted();
repository.save(process);
----

Keeping the row also gives you a queryable history of processes that ran, which deletion throws away. Which you want
depends on whether anyone will ask.

== Trade-offs

|===
| Good | Not so good

a|
* The most familiar shape, and the fewest new ideas to take on.
* State is queryable, indexable and reportable.
* Works regardless of where the events it reacts to come from.
* No requirement on tags, event stores, or ownership of the other context.

a|
* Two effects per step, and they only commit together because a transaction manager is present.
* The state is a second source of truth that can drift from the events.
* Ending is a decision you have to make and get right.
|===
