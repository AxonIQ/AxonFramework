= State in a Repository
:navtitle: State in a repository
:reftext: State in a repository

The process keeps what it needs to remember in a table of its own. It is the most familiar of the approaches and the
right place to start if you are unsure.

The state is an ordinary record with ordinary columns, which is the whole point: you can query it, index it, report on
it, and join it. A process whose progress somebody will eventually ask about wants exactly that.

== When to use it

Use this when the process genuinely has to remember something, and either you want that memory queryable or the events
it reacts to are not all in an event store you own.

It is the only approach with no prerequisites at all beyond a place to write. If the payment side is a third-party
provider whose events you merely receive, this still works, where
xref::state-from-domain-events.adoc[deriving state from domain events] cannot.

<1> The idempotency check. A redelivered `BikeRequested` must not ask for payment a second time.
<2> Returning the result of the dispatch is what makes the processor await the command and leave the tracking token
where it is if it failed.
<3> The write happens only after the command succeeded, and is deferred into the unit of work that also stores the
token.
<4> Ending the process by forgetting it.

Three of those four callouts are about ordering and transactions. That is the price of this approach, and it is worth
being explicit about why each is written the way it is.

[#ordering]
== Why dispatch comes before the write

Writing the row first and dispatching second looks equivalent and is not. If the dispatch fails, the handler fails, the
token is not committed and the event is redelivered. The row now says payment was already asked for, so the guard on
the next delivery skips the work. The process is wedged permanently, having never asked for payment, and nothing in the
logs points at the row that caused it.

Dispatching first has no such failure mode. If the command fails, nothing was written, the redelivery tries again. If
the command succeeded but the commit did not, the redelivery sends the command again, and the receiver's idempotency
absorbs it.

[#transaction]
== Why the write is deferred to the commit

The obvious way to write after a successful dispatch is a callback on the command's future:

[source,java]
----
// Do not do this
return dispatcher.send(command)
                 .getResultMessage()
                 .thenRun(() -> repository.save(state));
----

That callback may run on a thread with no transaction bound to it, and it runs whether or not the batch later commits.
Registering the save on the processing context instead puts it in the same unit of work that stores the tracking
token, so the two commit together:

[source,java]
----
return dispatcher.send(command)
                 .getResultMessage()
                 .thenRun(() -> context.runOnPrepareCommit(ignored -> repository.save(state)));
----

This is the single most important detail on this page. A process whose state can commit without its token, or the
reverse, will drift, and the drift only shows up under failure.

[#ending]
== Ending the process

Deleting the row is the simplest way to end, and it is what the sample does. It is safe here for a specific reason:
every command this process sends is idempotent, so a redelivery arriving after the row is gone restarts the process,
re-dispatches, and the receiving context declines to append anything.

If that were not true, deleting would be unsafe, and you would keep a tombstone row instead:

[source,java]
----
process.markCompleted();
repository.save(process);
----

Keeping the row also gives you a queryable history of processes that ran, which deletion throws away. Which you want
depends on whether anyone will ask.

== Trade-offs

|===
| Good | Not so good

a|
* The most familiar shape, and the fewest new ideas to take on.
* State is queryable, indexable and reportable.
* Works regardless of where the events it reacts to come from.
* No requirement on tags, event stores, or ownership of the other context.

a|
* Two effects per step, so the ordering and transaction rules must be observed by hand.
* The state is a second source of truth that can drift from the events.
* Ending is a decision you have to make and get right.
|===
