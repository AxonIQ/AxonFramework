= Sagas and Process Managers
:navtitle: Sagas
:reftext: Sagas

Some business processes are longer than a single decision. A rental is not paid for in the same breath as it is
requested, an order is not shipped the instant it is placed, and a booking is not confirmed the moment it is made.
These processes span more than one entity, often more than one bounded context, and they take time.

Axon Framework 4 gave that shape a name and a construct: the `@Saga`. A saga was described as a special kind of event
handler, one that manages a business transaction spanning several aggregates, remembering what it has seen so far and
deciding what should happen next. That description is still exactly right. What has changed is that Axon Framework 5
no longer ships one particular implementation of it.

== Why there is no Saga class in Axon Framework 5

An Axon Framework 4 saga made three decisions on your behalf, and they were not separable:

* State was *state-sourced*. The saga instance was serialized into a `SagaStore` as an opaque blob, so the only way to
  ask a question of it was to load and deserialize it.
* Correlation went through *association values*, maintained with `SagaLifecycle.associateWith(...)`.
* Life cycle was framework-managed, through `@StartSaga` and `@EndSaga`.

Those defaults suit some processes well and others badly. A process that needs to be queried, reported on, or joined
against wants columns rather than a blob. A process whose correlation is derivable does not need association values at
all. A process that is really a handful of independent reactions does not need a life cycle.

Axon Framework 5 hands each of those decisions back to you. A process is written with the same building blocks as
everything else: event handlers that react, command handlers that decide, and whichever form of state the process
actually needs. This page describes the shapes that combination takes, and when to reach for each.

There is a fifth option, xref::workflows.adoc[Workflows], which takes the opposite approach: the process is written
as a single method that reads top to bottom, and the framework persists the position within it. It is part of Axoniq
Framework rather than Axon Framework, is in preview, and requires a licence, so it is discussed separately.

[#two-rules]
== Two rules that apply to every approach

Whatever shape you choose, a process reacts to events and sends commands. That combination has two consequences you
cannot design away, and most process bugs are a violation of one of them.

=== Commands a process sends must be idempotent

An event processor delivers at least once. If the tracking token is not committed, the event arrives again, and the
process reacts again. Every command it sends will therefore sometimes be sent twice.

The fix belongs in the receiver, not the sender. Approving an already-approved request, or cancelling an
already-settled payment, should append nothing and report success:

[source,java]
----
@CommandHandler
void handle(ApproveRequest command, @InjectEntity @Nullable Bike bike, EventAppender appender) {
    if (bike == null || !Objects.equals(bike.reservedBy(), command.renter()) || bike.reservationConfirmed()) {
        return; // <1>
    }
    appender.append(new BikeInUse(command.bikeId(), command.renter(), bike.rentalId()));
}
----
<1> Silently doing nothing is the point. A redelivery must be indistinguishable from the first delivery.

A useful trick is to make the receiver's decision model naturally exclusive. If a payment is keyed by the caller's own
reference rather than by an identifier the payment mints, then "prepare a payment for this reference" cannot happen
twice, and no guard has to be remembered.

=== Progress must not be recorded before the command succeeds

There is no transaction spanning "dispatch a command" and "write down that I dispatched it". Recording first is a
quiet and permanent bug: the dispatch fails, the handler fails, the token is not committed, the event is redelivered,
and the recorded progress now makes the process skip the work it never did.

The order that works is: dispatch, wait for success, then record.

[IMPORTANT]
====
Returning the `CompletableFuture` from the event handler is what makes the processor wait for the command and leave
the token where it is on failure. Dropping the `return` turns the whole thing into fire-and-forget: the token advances,
the command is lost, and the process waits forever. This is also what replaces the version 4 practice of scheduling a
retry deadline.
====

Note that two of the approaches below sidestep this rule entirely, because they never record anything of their own.

[#choosing]
== Choosing an approach

[cols="1,2,2,2",options="header"]
|===
| Approach | Good for | Costs | Requires

| xref::state-in-a-repository.adoc[State in a repository]
| The first thing to try. Familiar from version 4, queryable, and works no matter where the events it reacts to come
from.
| Two things happen per step, so the ordering rule above has to be observed by hand.
| A store you can write to in the processor's transaction.

| xref::state-from-domain-events.adoc[State derived from domain events]
| Processes whose state is already implied by events you own. Stores nothing, so nothing can fall out of step.
| Invisible: a step that produces no event leaves no trace. One extra read per event.
| One event store, and a tag on the correlated events of both contexts.

| xref::state-from-process-events.adoc[State from the process's own events]
| Long or regulated processes where you want an audit trail of the process itself, and for integrating with systems
whose events are not yours.
| The most machinery of the four: its own events, and either an extra command or an append from an event handler.
| Nothing beyond an event store of your own.

| xref::automation-slices.adoc[Automation slices]
| Vertical Slice Architecture and Event Modelling. The best transactional profile, since each slice does exactly one
thing.
| No single place describes the process any more. Only an event model shows it whole.
| Nothing. Most slices need no state at all.

| xref::workflows.adoc[Workflows]
| Processes that are genuinely complicated: many steps, real branching, compensation, or waiting that matters. The
flow is written as a flow.
| A dependency and a licence. Overkill for a process of three reactions.
| Axoniq Framework, currently in preview.
|===

If you are migrating an existing version 4 saga and want the smallest step, start with
xref::state-in-a-repository.adoc[state in a repository]: it is the closest to what you have. If you are writing
something new and already structure your application in vertical slices, start at the other end with
xref::automation-slices.adoc[automation slices], and reach for a process class only when you find you need one.

[TIP]
.Try removing the need for state first
====
Before choosing where to keep process state, check whether you need any. A large share of version 4 sagas kept state
purely to remember an identifier they could have computed.

If the process can derive its correlation, for example by using the rental identifier as the payment reference, then
both directions are free: outbound it computes the reference, inbound it reads the reference off the event. Several of
the approaches below become dramatically simpler, and two of them become possible at all, because of that one choice.
====

[#sequencing]
== Sequencing

A pooled streaming event processor handles many processes concurrently. Events belonging to *one* process must still
be handled in order, or a `PaymentPrepared` can still be in flight while the `PaymentConfirmed` that supersedes it is
already being processed.

<1> All events of one rental are handled sequentially; different rentals still run in parallel.
<2> Returning the result is what makes the processor await the command.

Where a component handles events from two contexts that name the correlation differently, no single
`PropertySequencingPolicy` spans them. Write a policy that routes on the message's `QualifiedName` and delegates to a
typed policy per event type; the example module contains one.

[WARNING]
====
Two mistakes in such a policy are easy to make and hard to see.

Extract the *raw* correlation value, not a typed wrapper. Returning `RentalId` from one side and `PaymentReference`
from the other means the two never compare equal, so the contexts land in separate sequences and the policy silently
does nothing.

Target *concrete* payload types, never a shared supertype. Converting to an interface works in memory, where the
payload is already an object, and fails against a real event store, where it arrives as bytes no converter can turn
into an interface. A test using plain objects will not catch this.
====

[#testing]
== Testing

`AxonTestFixture` tests a process without any special support. Publish the events that lead up to the moment you care
about, then assert on the command the process sends:

[source,java]
----
fixture.given()
       .events(new BikeRequested(bikeId, renter, rentalId),
               new PaymentPrepared(paymentId, PRICE, paymentReferenceFor(rentalId)),
               new PaymentConfirmed(paymentId, paymentReferenceFor(rentalId)))
       .then()
       .await(result -> result.commandsSatisfy( // <1>
               commands -> assertThat(payloadsOf(commands)).contains(new ApproveRequest(bikeId, renter))
       ), Duration.ofSeconds(5));
----
<1> `await` is required: a pooled streaming processor runs on its own threads, so the command has not been sent yet
when the given phase returns.

Two details save time. Filter assertions to the identifiers the test generated rather than asserting on the exact
recorded list, because the recording command bus accumulates across every test sharing a Spring context and is only
reset by a `when` phase that event-driven scenarios do not use. And keep correlation values unique per test, since a
value used as a tag makes one test's events visible to another test's criteria.

For the timeout path, see xref::deadlines.adoc[deadlines].
