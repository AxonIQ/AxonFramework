= Deadlines
:navtitle: Deadlines
:reftext: Deadlines

Most long-running processes need to give up eventually. A payment that never arrives, an approval nobody grants, a
confirmation that never comes: something has to notice and act.

Nothing schedules a callback into a process's own future for you, and this page describes what to do instead. The
result needs no scheduling infrastructure that understands your domain, and it is easier to test than a timer.

[TIP]
====
Where xref::workflows.adoc[[.advanced-framework]#Workflows#] are available to you they are the recommended answer, and none of
this page applies: waiting is an ordinary statement in the flow, so a timeout is written where it happens rather than
built out of a projection and a sweep.
====

== The shape of the replacement

A deadline consists of two things: a record of work that is outstanding, and something that periodically
notices when a piece of it has waited too long. Separating them gives you both without a scheduler that understands
your domain.

* A *projection* of outstanding work, built purely from events: a *to-do list*, in Event Modelling terms.
* A *sweep* that reads that projection and sends a command. This is an Event Modelling *automation* working that
  to-do list, the same purple building block that drives every other reaction in this guide, only triggered by what is
  overdue rather than by an event arriving.

.The timeout as its own event model, drawn on link:https://prooph-board.com[prooph board,role=external,window=_blank] (click to open full size)
image::EventModeling_PaymentDeadline.png[The payment timeout modelled as a projection and a sweep on prooph board,link=self,window=_blank]

Both halves are on the left of the model. `PaymentPrepared` puts a row on the green projection, and the purple sweeper
reads it. Neither writes anything the other depends on. The rest of this page relies on that property.

The right side of the model is the part a timeout is usually assumed not to
have. Giving up is not one decision in one place: the payment is called off, and only then does a further reaction
release the bike. The two bounded contexts never address each other, and what the rental side is finally told is
`RejectRequest`. Not that a clock ran out, not that a deadline elapsed. No timeout concept crosses the boundary at all.
The rental context stays ignorant that payments exist.

This model is drawn separately from
xref::bike-rental-event-model.adoc[the bike rental event model] on purpose. The sweep is a different actor on a different
schedule, and the projection is not part of any one approach: it is built from payment events, so it applies to every
approach in this guide equally.

[#a-command-not-an-event]
== Why the timeout becomes a command

The timeout is expressed as a command rather than an event.

A timer that fires *inside* a process is invisible from outside it, can only be triggered by waiting, and has to be
unscheduled when the process ends. None of that is necessary. Use an ordinary command that asks the process to give
up:

----
include::example$sagas/shared/RentalPaymentApi.java[tag=cancel-rental-payment,indent=0]
----

A command rather than an event, and the distinction matters. An event says something happened; the fact that a
timeout elapsed is not, by itself, a fact about the business. What the sweep wants is to *ask* the process to give up,
and the process may well decline because the payment arrived a moment ago. That is a request, which is a command, and
it has a receiver entitled to say no.

Publishing a `PaymentTimedOut` event instead would assert as fact something that has not been decided, and would leave
no natural place to decide it. It also loses the ability to reject: an event has no result.

Three things follow from expressing the timeout as a command, and all three are improvements:

* *Anyone can send it.* An operator, a support tool, a REST endpoint or a test, not only the scheduler.
* *It is testable without waiting.* This is why the sample can test a fifteen-minute timeout in milliseconds.
* *Cancellation disappears.* Nothing is scheduled, so nothing has to be unscheduled when the process ends. A command
  that arrives after the process is over simply finds nothing to do.

[IMPORTANT]
.Writes come from events, reads come from the schedule
====
The projection is written only by event handlers. The sweep only reads and dispatches.

That split is what makes the pattern safe. The list cannot drift from the event stream, because nothing else writes to
it, and the sweep has no state of its own to keep in step with anything. This is the same hazard that
xref::state-in-a-repository.adoc#ordering[keeping process state in a repository] has to work around by care,
avoided here by construction.
====

== Testing a timeout

`AxonTestFixture` cannot manipulate time. For that reason, the work is a method taking `Instant` rather than logic
inside the `@Scheduled` method. That also splits the testing into two halves that fail for different reasons.

=== The sweep

This test verifies that the sweep notices overdue work and leaves the rest alone. Because the projection removes a row when the payment settles,
the row disappearing is the observable proof that the sweep reached the payment side:

[source,java]
----
@Test
void givenOverduePayment_whenSweeping_thenItIsCalledOffAndLeavesTheList() {
    // given a payment that has been outstanding for a while
    var reference = someReference();
    fixture.given()
           .events(new PaymentPrepared(PaymentId.random(), PRICE, reference));
    awaitListed(reference);

    // when judged from far enough in the future
    sweeper.cancelOverduePayments(Instant.now().plus(Duration.ofHours(1))); // <1>

    // then the payment was called off, which is what takes it off the list again
    awaitNotListed(reference);
}
----
<1> No clock is faked and nothing sleeps. A fifteen-minute timeout is tested in microseconds.

[NOTE]
====
A sweep acts on *every* overdue item it finds, including ones other tests are relying on. Give a test class that
sweeps its own event store, which under Spring means a property set no other test class shares, so it gets a context
of its own.
====

=== The process

This test verifies that the process does the right thing when asked to give up. That is a different question, with no clock in it at all, so the
test says nothing about sweeping:

[source,java]
----
@Test
void givenPaymentNotConfirmed_whenAskedToGiveUp_thenRequestRejected() {
    // given a payment was asked for and never arrived
    fixture.given()
           .events(new BikeRegistered(bikeId, "city", "Vilnius"),
                   new BikeRequested(bikeId, renter, rentalId))
           .then()
           .await(result -> result.commandsSatisfy(commands -> assertDispatched(
                   commands, new PreparePayment(reference, PRICE)
           )), TIMEOUT) // <1>
           .and()
           .when()
           .command(new CancelRentalPayment(rentalId)) // <2>
           .then()
           .success()
           .await(result -> result.commandsSatisfy(
                   commands -> assertDispatched(commands, new RejectRequest(bikeId, renter))
           ), TIMEOUT);
}
----
<1> The payment is not published by the test: the process asks for it, and the payment side creates it. Waiting for
that command is what tells us the process has noticed this rental, which matters because the approaches that record
their own progress do so asynchronously. Asking one to give up before it has noticed would find nothing to give up on.
<2> Giving up is the *when*, because that is the action under test.

A single test driving the sweep and asserting on the released bike passes
or fails for at least three different reasons, and tells you nothing about which. Splitting the two tests avoids that ambiguity.

[#caveats]
== Where this pattern gets harder

The naive version looks simpler than it is. The following caveats apply before relying on it.

Every instance sweeps::
`@Scheduled` runs on all of them, so three instances dispatch each cancellation three times. Harmless when the command
is idempotent, but wasteful. Production deployments want a lock or a leader election.

A replay rebuilds the list with original timestamps::
Every historical outstanding item briefly looks overdue and is swept. This is survivable only because the receiver
ignores a cancellation of something already settled. The pattern leans on idempotency harder than it first appears.

Precision is the poll interval::
Fine for "give up after fifteen minutes". Not suitable for "act at 09:00:00 exactly". If you need precision, use a
real scheduler and have it send the same command.

The query must stay a query::
Filtering at the database on an indexed column, never loading everything and filtering in memory.

In summary, this replaces a deadline *manager* with a deadline *projection*. It is simple, replayable and
needs no new infrastructure, but it is approximate in time and duplicated across instances, and it is acceptable only
because every command it sends can be sent twice.

== Alternatives

If a scheduled projection does not fit, the command is still the right target and only the trigger changes.

* An external scheduler, such as Quartz or a cloud scheduler, sending the same command.
* A message broker's delayed delivery, if you already run one.
* link:https://docs.axoniq.io/axon-framework-reference/development/workflows/[Axoniq Framework Workflows,role=external,window=_blank],
  which handles waiting as a first-class concern. It is available as a preview and requires a licence for production
  use.

Because the timeout is a command, swapping the trigger changes nothing about the process itself.
