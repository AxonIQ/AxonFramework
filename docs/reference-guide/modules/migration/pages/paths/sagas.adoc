= Saga Migration
:navtitle: Sagas
:reftext: Saga migration

Axon Framework 5 allows you to replace the Axon Framework 4 `Saga` concept with existing core framework building blocks.
The familiar `@Saga` stereotype and related APIs will not be ported to the Axon Framework 5 core.
The same applies to the `DeadlineManager` and related APIs.
There will, however, be a legacy layer to allow migrating running sagas and deadlines.

For *new* processes, Axon Framework 5 allows several ways to implement them with the existing framework building blocks.
The xref:saga-guide:ROOT:index.adoc[Sagas and Process Managers] guide describes them in detail.

For sagas that are *already running* (considering business processes running for months), rewriting is not an option.
That case is served by the `axon-legacy` module, described in <<legacy-module>>.

[IMPORTANT]
====
For saga migration you need to consider two scenarios:

*Writing new processes:* Pick an approach from the
xref:saga-guide:ROOT:index.adoc[Sagas and Process Managers] guide and write it today.

*Migrating running sagas:* Use the Axon Framework 4 compatible APIs of the `axon-legacy` module to keep existing saga classes running until all legacy saga instances are drained naturally.
The legacy module should be treated as a way to finish existing instances, not to keep sagas in Axon Framework 5.
====

[#legacy-module]
== Running existing sagas on Axon Framework 5

The `axon-legacy` module exists to allow migrating to Axon Framework 5 while saga instances started on Axon Framework 4 are still running.
This can happen easily if you have business processes covered by sagas that span weeks or months until finished.
To allow a gradual migration, `axon-legacy` allows you to adopt running saga instances while not starting new instances, which should in the best case be covered by an Axon Framework 5 native implementation of the business process.

Specifically, the `axon-legacy` module brings forward the following Axon Framework 4 saga and deadline infrastructure adapted to the Axon Framework 5 APIs:

* `@Saga`, `@SagaEventHandler`, `@StartSaga`, `@EndSaga`, `SagaLifecycle` and the association-value mechanism
* `SagaStore` and its concrete implementations, to support existing saga stores
* `DeadlineManager` and `@DeadlineHandler`

The goal of the legacy module is to support your existing saga classes as is, by adding the `axon-legacy` module as a dependency to your project.

[NOTE]
====
The `axon-legacy` module is *under development* and scheduled for 5.4.0, so until it lands there is no supported way to upgrade an application with sagas in flight.

link:https://github.com/AxonFramework/AxonFramework/issues/3728[GitHub Issue #3728] tracks the saga side and
link:https://github.com/AxonFramework/AxonFramework/issues/3065[GitHub Issue #3065] the deadline side. Until they are
released, plan on the code-level migration below and on the drainage strategy in <<strategy>>.
====

The `axon-legacy` module is a migration aid and not intended to be a supported way to write new processes. `@StartSaga`
is deprecated on purpose for that, and starting new instances through the legacy module is not intended.
Existing instances receive their events and run to completion; new work goes to the Axon Framework 5 implementation you write alongside.

== Mapping Axon Framework 4 saga concepts to Axon Framework 5

An Axon Framework 4 saga provides opinionated technical infrastructure to implement long-running business processes:

* State is *state-sourced*, the saga instance is serialized into a `SagaStore` as an opaque blob
* Correlation requires *association values*, maintained with `SagaLifecycle.associateWith(...)`.
* Life cycle is framework-managed, through `@StartSaga` and `@EndSaga`.

While those choices suit some processes well, they limit the options to implement your long-running processes.

Axon Framework 5 broadens that choice and gives different options to implement long-running processes depending on your needs.
The xref:saga-guide:ROOT:index.adoc[Sagas and Process Managers] guide describes these approaches in detail, the following sections provide a mapping of Axon Framework 4 saga concepts to Axon Framework 5.

[cols="1,2",options="header"]
|===
| Axon Framework 4 | Axon Framework 5

| `@Saga`
| A `@Workflow` (see <<workflows,Workflows>>), or an ordinary component with `@EventHandler` methods.

| `@SagaEventHandler(associationProperty = "...")`
| `awaitEvent(...)` in combination with `associate(...)` for a <<workflows,Workflow>>, or a plain `@EventHandler` resolving correlation by the entity identifier, a property, or your own `EntityIdResolver`.

| `@StartSaga`
| `@Workflow(startOnEvent = "...")` for a <<workflows,Workflow>>, the first event that concerns a process creating its state for a plain `@EventHandler` approach.

| `@EndSaga`
| the end of the workflow definition for a <<workflows,Workflow>>, for a plain `@EventHandler` depending on the approach: delete the row, append a completion event, or nothing at all when state is derived.

| `SagaLifecycle.associateWith(...)`
| `awaitEvent(...)` in combination with `associate(...)` for a <<workflows,Workflow>>, a tag on the event, or a derived correlation value. See the tip below.

| `SagaLifecycle.end()`
| a `return` statement in the workflow definition for a <<workflows,Workflow>>, or whatever the chosen approach records as "finished".

| `SagaStore`, `SagaRepository`
| Your regular event store for a <<workflows,Workflow>>, a repository of your own, an event-sourced entity, or nothing.

| `DeadlineManager`, `@DeadlineHandler`
| `sleep(...)` for a <<workflows,Workflow>>, or a projection of outstanding work plus a scheduled sweep that sends a command. See
xref:saga-guide:ROOT:deadlines.adoc[deadlines].

| `SagaTestFixture`
| The dedicated <<workflows,Workflows>> Test infrastructure, or `AxonTestFixture` publishing events in the given phase and asserting on dispatched commands for a plain `@EventHandler` approach.
|===

[#workflows]
[.axoniq-feature]
== Replacing sagas with Workflows

The recommended replacement for sagas are xref:saga-guide:ROOT:workflows.adoc[Workflows].
They are the recommended way to orchestrate a process.
The flow is written as a single method that reads top to bottom, using the regular event store for an event-sourced persistence of the process.

[NOTE]
====
Workflows are an Axoniq Framework feature and require an Axoniq license to run in production.
Workflows are currently available as a preview and can be tried out without a license.
====

As described above, saga concepts translate pretty well onto Workflow concepts:

* The association value becomes the workflow's identifier and manual `associate(...)` invocations when waiting on events.
* Each `@SagaEventHandler` becomes a step.
* `@EndSaga` becomes the end of the workflow definition method.
* Deadlines are expressed as explicit wait or timeout on an event in the workflow.

What is different from Axon Framework 4 sagas is the processes state.
Workflows do not rely on a persistent storage of the processes state, but instead use dedicated workflow events stored in the regular event store to source the state of the process.
That means, a running saga holding a serialized instance in a `SagaStore` cannot be handed to a workflow.
Running Axon Framework 4 saga instances need to drain as described in <<strategy>>, whichever replacement you pick.

[#deadlines]
== Migrating deadlines for sagas

Axon Framework 4 allowed you to schedule deadlines to defer reactions in time for sagas.
Axon Framework 5 does not bring back direct support for deadlines, but provides different capabilities to achieve the same functionality.

In Axon Framework 4 you would set up a deadline using the `DeadlineManager` to trigger in the future and handle the trigger when the time elapsed by implementing a `@DeadlineHandler` - most probably taking some attributable action like sending a command.

In Axon Framework 5 you can achieve the same by choosing the scheduling library of your choice, setting up a scheduled task wiring in the `CommandGateway` and sending the command via the gateway when the scheduled task triggered.
Making sure the command handler you implement acts idempotent guarantees that an action scheduled for a process that progressed otherwise meanwhile is simply ignored.

For additional details on deadlines for long-running processes in Axon Framework 5 check out the xref:saga-guide:ROOT:deadlines.adoc[deadlines] page.

[#choosing]
== Choosing a replacement

Not every saga should become a workflow.
Simple processes that only consist of a limited set of independent reactions can be implemented by means of regular Axon Framework 5 event- and command handlers.
The xref:saga-guide:ROOT:index.adoc#long_running_processes[guide] compares the alternatives in more details.
In short:

* xref:saga-guide:ROOT:state-in-a-repository.adoc[State in a repository] is the closest to how an Axon Framework 4 saga worked.
Start here if you are porting an existing saga.
* xref:saga-guide:ROOT:state-from-context-events.adoc[State from context events] avoids persistent state in a repository.
This is only possible if all involved contexts write to one event store and their events carry a tag you can select on.
* xref:saga-guide:ROOT:state-from-process-events.adoc[State from process events] suits integration with systems whose
events are not yours, and gives an audit trail of the process.
* xref:saga-guide:ROOT:vertical-slices.adoc[Vertical slices] break the process into independent reactions, which fits
Vertical Slice Architecture and Event Modelling.

[#strategy]
== Migrating an application with running sagas

Whether or not you use the <<legacy-module,legacy module>>, you need to migrate running saga instances by *drainage*, that means letting saga instances created by Axon Framework 4 finish in a regular way while starting new process instances with an Axon Framework 5 compliant implementation.

Without the legacy module, draining old saga instances needs to happen in an Axon Framework 4 deployment kept alive alongside the Axon Framework 5 application that migrated the process to the selected approach.
The legacy module allows you to drain the old saga instances alongside the upgraded application in a single Axon Framework 5 application.
Either way (using the legacy-module for drainage or not), new sagas must not be started from the Axon Framework 4 legacy code.

The main steps for migrating running sagas outline as follows:

. *Stop starting new sagas.* Remove the `@StartSaga` annotation from the Axon Framework 4 saga.
Existing instances keep receiving their events and run to completion; no new ones are created.

+
[source,java]
----
@Saga
public class PaymentSaga {

    // @StartSaga  <1>
    @SagaEventHandler(associationProperty = "bikeId")
    public void on(BikeRequestedEvent event) {
        // ...
    }
}
----
<1> Removing this is the whole trick. The saga can still advance and still end; it just cannot begin.

. *Keep the old saga running.* With the legacy module, add the dependency and let the existing class continue against its existing saga store in the upgraded application.
Without it, keep the Axon Framework 4 deployment alive to drain existing saga instances without creating new ones.
. *Implement the process in Axon Framework 5* using one of the approaches above, and let it handle the same trigger
event.
. *Wait for the old instances to drain.* Monitor the `SagaStore` for active instances and watch the count fall to zero.
How long that takes depends on your longest running process.
. *Retire the Axon Framework 4 saga* once there are no more active instances in the `SagaStore`. The legacy saga code together with the `SagaStore` table, its deadline scheduler, and the legacy dependency can be removed once all instances are drained.

Scheduled deadlines drain the same way.
As long as there are saga instances relying on deadline instances the Axon Framework 4 `DeadlineManager`, or the legacy module's port of it need to be kept online.

== Testing

A saga kept running on the <<legacy-module,legacy module>> keeps its existing tests.
For the process migrated to Axon Framework 5, new tests need to be established.
The existing `AxonTestFixture`
can be used to achieve that: publishes events that drive the process and asserting on the commands the process is expected to send.

The mapping below covers the common cases:

[cols="1,2",options="header"]
|===
| `SagaTestFixture` | `AxonTestFixture`

| `givenNoPriorActivity()`
| `given().noPriorActivity()`

| `givenAPublished(event)` / `andThenAPublished(event)`
| `given().events(event, ...)`

| `whenPublishingA(event)`
| `when().event(event)`, or include it in `given().events(...)` and assert with `await`

| `expectDispatchedCommands(command)`
| `then().await(result -> result.commandsSatisfy(...))`

| `expectActiveSagas(n)`
| No equivalent. Assert on the observable outcome, or on your own state if the approach keeps any.

| `whenTimeElapses(duration)`
| No equivalent. Structure the timeout so it can be invoked directly; see xref:saga-guide:ROOT:deadlines.adoc[deadlines].
|===
