= Event-Sourced Entities
:navtitle: Event-sourced entities

An event-sourced entity stores no state directly.
Instead, every state change is recorded as an event, and the entity's current state is reconstructed by replaying those events in order.
This makes the event log the single source of truth, giving you a complete and immutable audit trail of everything that ever happened to the entity.

[TIP]
====
If you are unfamiliar with event sourcing, see xref:events:index.adoc#core-concepts[Events core concepts] for an introduction to the concept.
====

[#_entity_members]
== Entity members

An event-sourced entity consists of four types of members:

* **Creational command handlers**: static methods that handle the command that creates the entity.
They validate the command and append the creation event.
* **Instance command handlers**: instance methods that handle commands on an already-existing entity.
They validate the command against current state and append events.
* **Event sourcing handlers**: instance methods that apply events to update the entity's state fields.
They must never contain business logic, only state assignments.
* **Entity creator**: a constructor or static factory method that tells Axon how to construct the initial entity instance before replaying events.

<4> No-arg constructor used as the entity creator.

[IMPORTANT]
====
Command handlers validate and append events; they must never write to entity state fields.
Event sourcing handlers update state; they must contain no business logic.

This separation is critical because event sourcing handlers also run during replay when the entity is loaded from its event stream.
Any business logic in an event sourcing handler would execute unexpectedly during replay.
====

[TIP]
====
An entity only needs the state required to make decisions about incoming commands.
An event sourcing handler is only needed when the resulting state change is relevant for validating future commands.
====

=== Static Event Sourcing handlers

An event sourcing handler can also be `static`, taking the current entity state as its first parameter and returning the next state:

[source,java]
----
@EventSourcingHandler
static Course on(@Nullable Course state, CourseCreated event) {
    return new Course(event.courseId(), event.name());
}
----

The current-state parameter is `null` while the entity does not exist yet.
A static handler therefore covers a case an instance handler cannot: it can create the entity from its first event.
It can also evolve an existing instance (returning the next state), or, while the state is still `null`, return `null` to decline creating the entity for that event.

Use a static event sourcing handler when an entity should not exist until a specific event establishes it, without declaring a first-event-based xref:commands:entities/entity-creator.adoc[entity creator] for that event.
An instance handler still requires an existing entity, so it only runs once a static handler (or an entity creator) has produced one.

The state parameter is optional.
When a handler creates the entity purely from the event and does not need the previous state, you can omit it:

[source,java]
----
@EventSourcingHandler
static Course on(CourseCreated event) {
    return new Course(event.courseId(), event.name());
}
----

Because this form has no access to the prior state, it always produces a fresh instance from the event.
Use it only for an event that establishes the entity; if that event type could also arrive once the entity already exists, it would replace the current state.
Keep the state parameter (marked `@Nullable`) whenever the next state depends on the previous one.

[NOTE]
====
Once an entity exists, it stays non-null.
A static event sourcing handler must not return `null` for an already-existing entity: doing so is rejected.
Model the end of an entity's lifecycle as a terminal state, for example a `closed` flag, rather than as a `null` entity.
====

=== Entity creator

The entity creator method can come in several forms.
You can choose a no-argument, identifier-based, or first-event-based entity creator method.
These options allow you to derive a mutable **and** immutable entity depending on the preferred structure.

Depending on the configuration style, you either use the `EventSourcedEntityFactory` (declarative) or `@EntityCreator` (automated) to define the entity creator method.

For more details on the options, see the xref:commands:entities/entity-creator.adoc[Entity creator] section.

== Configuring an entity

Three approaches are available to wire this entity into Axon:

. <<_declarative,Declarative>>: no annotations on the entity class. Wire handlers and lifecycle programmatically with `EventSourcedEntityModule.declarative()`.
. <<_autodetected,Autodetected>>: annotate with `@EventSourcedEntity`. Register with `EventSourcedEntityModule.autodetected()`.
. <<_spring_boot,Spring Boot>>: annotate with `@EventSourced`. Axon's auto-configuration detects and registers it automatically.

[#_spring_boot]
=== Spring Boot

In Spring Boot, annotate the entity with `@EventSourced` instead of `@EventSourcedEntity`.
Axon's auto-configuration detects and registers it automatically; no explicit configuration class is required.
The entity class structure is otherwise identical to the <<_autodetected,autodetected>> approach.

== Placing handlers on the entity vs. a separate component

Command handlers can be placed directly on the entity class (as shown above) or kept in a separate component that receives the entity as a parameter via `@InjectEntity`.
Both approaches are valid; choose based on how you want to structure your codebase.

Placing handlers on the entity keeps all logic for that entity in one class.
A separate component lets you organize code by use case rather than by entity, which aligns with Vertical Slice Architecture.

See xref:commands:entities/stateful-command-handler.adoc[Stateful command handlers] for the full pattern.
