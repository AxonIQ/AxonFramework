= Spring Boot Integration

The Axon Framework Spring Boot extension maps Axon's configuration API onto the Spring Application Context.
It provides auto-configuration so that, in most cases, adding the starter dependency is all that is needed to get a fully configured Axon application.
This page explains how the Spring integration builds on the same concepts described in the rest of this chapter.

For setup instructions, Spring Boot version support, and event processor-specific configuration, see
xref:ROOT:spring-boot-integration.adoc[Spring Boot integration].

== How Spring uses the configuration API

The Spring integration does not bypass the configuration API: it implements it.
In practice, this means the Spring `ApplicationContext` and Axon's `Configuration` share the same set of components: any infrastructure component Axon provides (the `CommandBus`, `EventStore`, `QueryBus`, and so on) is automatically made available as a Spring bean, injectable like any other bean.

The reverse also holds.
If you declare your own `@Bean` of a matching infrastructure type, Axon picks it up and uses it instead of its own default, no further wiring required:

[#axon-components-as-spring-beans]
Components registered through the `ComponentRegistry`, whether by Axon's defaults or by a `ConfigurationEnhancer`, become Spring beans as follows:

* A component registered by type only becomes a bean named after the fully qualified name of that type, for example `org.axonframework.messaging.commandhandling.CommandBus`.
Injecting the type yields this component, also when named components of the same type exist.
* A component registered under a name becomes a bean with that name.
Inject it with `@Qualifier` carrying the component name.
Without a qualifier, Spring only injects a named component when it is the only candidate for the type.

When Axon looks up a component by type and several beans of that type exist, it uses the `@Primary` bean or the bean named after the fully qualified name of the type.
Without either, the lookup throws an `AmbiguousComponentMatchException`, so the application fails to start when Axon needs that component during startup.

Properties that refer to a component by its name, such as the `source` and `token-store` settings of an event processor, use these bean names.
A lookup by name returns the bean with that name.
Without such a bean, it returns the single bean of the requested type that has the name as an alias or in its `@Qualifier`.
When several beans of that type have the name as their qualifier, the lookup throws an `AmbiguousComponentMatchException`.

[#handling-component-detection]
== Message handler and entity detection

The Spring Boot Starter automatically detects Axon components in the Application Context:

* Methods annotated with `@CommandHandler`, `@EventHandler`, or `@QueryHandler` on any Spring bean are registered as message handlers with the appropriate bus.
* Classes annotated with `@EventSourced` are registered as event-sourced entities.

A single `@Component` can combine all three handler types; Axon discovers each annotated method independently:

[source,java]
----
include::example$configuration/spring/GiftCardHandler.java[tag=message-handling-component-example]
----

Handler discovery happens through `MessageHandlerConfigurer` and `MessageHandlerLookup`, which scan the bean factory for beans implementing `CommandHandlingComponent`, `EventHandlingComponent`, or `QueryHandlingComponent`, as well as beans with annotated handler methods.
Discovered handlers are wrapped into a `CommandHandlingModule` and `QueryHandlingModule`, and discovered `@EventSourced` entities into an `EventSourcedEntityModule`, each registered on the `ComponentRegistry` the same way a manually built xref:module.adoc[Module] would be.

[#axon-properties]
== Axon properties

Besides beans, decorators, and enhancers, several parts of the auto-configuration can be tuned directly through `application.properties` or `application.yml`, without writing any code:

[cols="1,2"]
|===
|Property |What it does

|`axon.axonserver.enabled`
|Enables or disables the Axon Server connector integration. Defaults to `true` when the connector is on the classpath.

|`axon.eventhandling.processors.<name>.*`
|Configures an individual event processor: mode, initial segment count, batch size, thread count, and more. See xref:#event-processor-configuration[Event processor configuration] below for the full reference.

|`axon.eventhandling.defaults.pooled.*` / `axon.eventhandling.defaults.subscribing.*`
|Default settings for all pooled streaming or all subscribing event processors. See xref:#global-event-processor-defaults[Global event processor defaults].

|`axon.eventhandling.tokenstore.claim-timeout`
|How long a streaming event processor waits before forcing a claim on a token segment that has not been updated.

|`axon.eventstorage.jpa.*`
|Tuning for the JPA-based event storage engine: batch size, gap cleaning threshold, gap timeout, and polling interval.

|`axon.converter.general` / `axon.converter.messages` / `axon.converter.events`
|Selects the `Converter` implementation used for general data (such as snapshots), message payloads, and event payloads respectively.

|`axon.timeout.*`
|Enables and tunes timeouts for transactions and message handlers (commands, events, queries, and deadlines).

|`axon.tracing.*`
|Enables and tunes OpenTelemetry-based tracing for Axon's infrastructure components. See xref:monitoring:tracing.adoc[Tracing] for the full property reference.

|`axon.update-check.disabled` / `axon.update-check.url`
|Disables Axon's startup update-check ping, or points it at a different URL.
|===

[#event-processor-configuration]
== Event processor configuration

Spring Boot provides two approaches to configure event processors: properties-based configuration, covered as part of getting started in xref:ROOT:spring-boot-integration.adoc#event-processor-configuration[Event processor configuration], and programmatic, type-safe configuration through `EventProcessorDefinition` beans, covered below.

Reach for properties-based configuration when the configuration is simple and doesn't require custom logic, settings vary per environment, or you're still prototyping.
A simple property-based setup looks as follows:

[source,properties]
----
axon.eventhandling.processors.my-processor.mode=pooled-streaming
axon.eventhandling.processors.my-processor.initial-segment-count=4
----

Reach for `EventProcessorDefinition` beans instead when you need fine-grained control over handler assignment, the configuration requires conditional logic, type safety and IDE support matter, or you want to share configuration between environments programmatically.

* **IDE support** - Better autocompletion and refactoring support

==== Configuration precedence

When using multiple configuration approaches:

1. Global customization beans are applied last, after `EventProcessorDefinition` beans
2. `EventProcessorDefinition` beans take precedence over properties-based configuration
3. Properties of a specific processor (`axon.eventhandling.processors.<name>.*`) take precedence over the global defaults (`axon.eventhandling.defaults.<type>.*`)
4. If a handler matches multiple `EventProcessorDefinition` selectors, an `AxonConfigurationException` is thrown at startup
5. Handlers not matched by any `EventProcessorDefinition` are assigned based on their package name (default behavior)

To avoid conflicts, ensure each handler is matched by at most one `EventProcessorDefinition` using mutually exclusive selectors.

For comprehensive event processor configuration examples and detailed information, see xref:events:event-processors/streaming.adoc[Event Processors].

[#global-event-processor-defaults]
=== Global event processor defaults

Settings that apply to all event processors of one type are configured under `axon.eventhandling.defaults`.
Pooled streaming processors read `axon.eventhandling.defaults.pooled.*`, subscribing processors read `axon.eventhandling.defaults.subscribing.*`:

[source,properties]
----
axon.eventhandling.defaults.pooled.batch-size=50
axon.eventhandling.defaults.pooled.thread-count=8
axon.eventhandling.defaults.pooled.initial-token=head
axon.eventhandling.defaults.subscribing.source=myEventSource
----

A processor starts from the defaults of its type, and each property set on `axon.eventhandling.processors.<name>.*` overrides the matching default.
The `mode` property is not a default, as it selects the type.
A processor without a `mode` property is a pooled streaming processor.

Settings that properties cannot express, such as a dead-letter queue, an error handler, or interceptors, are applied to all processors of a type through `PooledStreamingEventProcessorModule.Customization` and `SubscribingEventProcessorModule.Customization` beans:

[#event-processor-properties]
== Event processor properties

All properties are set per processor under `axon.eventhandling.processors.<name>.`, or as a default for all processors of a type under `axon.eventhandling.defaults.pooled.` and `axon.eventhandling.defaults.subscribing.`.

[cols="2,1,1,3"]
|===
|Property |Applies to |Default |Description

|`mode`
|Both
|`pooled`
|Type of the processor: `pooled` or `subscribing`. Not available as a default.

|`source`
|Both
|Unset
|Name of the bean to read events from. When unset, a pooled processor reads from the event store and a subscribing processor from the event bus.

|`initial-segment-count`
|Pooled
|`16`
|Number of segments created when the processor starts for the first time.

|`thread-count`
|Pooled
|`4`
|Maximum number of threads used to process events.

|`batch-size`
|Pooled
|`1`
|Maximum number of events processed in a single batch.

|`token-store`
|Pooled
|Unset
|Name of the `TokenStore` bean. When unset, the bean named `tokenStore` is used, or the single `TokenStore` bean of the application.

|`token-claim-interval`
|Pooled
|`5000`
|Time to wait after a failed attempt to claim a token, in the unit of `token-claim-interval-time-unit`.

|`token-claim-interval-time-unit`
|Pooled
|`MILLISECONDS`
|`TimeUnit` of `token-claim-interval`.

|`claim-extension-threshold`
|Pooled
|`5000`
|Time in milliseconds after which a work package extends the claim on its token when no events are handled.

|`coordinator-claim-extension`
|Pooled
|`false`
|Whether the coordinator extends the claims of the work packages. Enable when event handling regularly takes longer than the claim timeout of the token store.

|`sequencing-policy`
|Pooled
|Unset
|Name of the `SequencingPolicy` bean applied to components without a more specific policy.

|`initial-token`
|Pooled
|`default`
|Position to start from when the processor has no token: `default` (first position of the event stream), `tail` (first position), `head` (latest position, only events appended afterwards are handled), or `at_timestamp`.

|`initial-token-timestamp`
|Pooled
|Unset
|ISO-8601 instant, such as `2026-01-01T00:00:00Z`, to start from. Required when `initial-token` is `at_timestamp`, ignored otherwise.
|===

The application fails to start when `initial-token` is `at_timestamp` and `initial-token-timestamp` is missing.
See xref:events:event-processors/streaming.adoc#initial_token_config[Initial token] for the programmatic configuration.

[#spring-and-axon-impl-details]
== Implementation details

The classes below are what make the behavior above possible.
You will not typically interact with them directly, but they are useful to know when diagnosing configuration issues:

`SpringAxonApplication`::
A Spring `@Component` that implements `ApplicationConfigurer`.
It holds a `SpringComponentRegistry` and a `SpringLifecycleRegistry` and delegates to them when `componentRegistry(...)` or `lifecycleRegistry(...)` are called.
It is the Spring equivalent of `DefaultAxonApplication` used in plain Java setup.

`SpringComponentRegistry`::
A Spring `BeanPostProcessor` and `BeanFactoryPostProcessor` that implements xref:registries.adoc#component-registry[`ComponentRegistry`].
It connects Axon's component model to the Spring bean lifecycle.
Registrations made through `registerComponent`, `registerDecorator`, and `registerEnhancer` are all stored here and applied when Spring initializes beans.

`SpringLifecycleRegistry`::
A xref:registries.adoc#lifecycle-registry[`LifecycleRegistry`] backed by Spring's `SmartLifecycle` mechanism.
`onStart` handlers are invoked during Spring's context startup phase; `onShutdown` handlers are invoked during Spring's context close phase.

Because `SpringAxonApplication` implements `ApplicationConfigurer`, you can use the same `MessagingConfigurer`, `ModellingConfigurer`, or `EventSourcingConfigurer` wrapping pattern in a Spring context.
The `SpringAxonApplication` bean is the root configurer that gets wrapped.

The `SpringComponentRegistry` makes the behavior described above possible in two ways.
As a `BeanPostProcessor`, it checks, right after Spring creates a bean, whether any registered decorator or enhancer targets that bean's type; if so, the decorator is applied and the wrapped instance is used in place of the original, so the standard Axon decorator mechanism works seamlessly for Spring-managed beans.
As a `BeanFactoryPostProcessor`, it allows the resulting `Configuration` to look up any bean from the Spring `ApplicationContext`, not just those explicitly registered with the `ComponentRegistry`.
This is what makes the `CommandBus` bean shown above available to Axon: it is treated as the registered `CommandBus` component, and any decorator registered through the `ComponentRegistry` (or through a `ConfigurationEnhancer`) is applied on top of it.

Components registered with the `ComponentRegistry` become bean definitions when the registry initializes, just before Spring creates the first application bean.
A named component is registered as a fallback bean (`AbstractBeanDefinition#setFallback`).
When an unqualified injection point matches both the type-level component and named components, Spring selects the single non-fallback candidate: the type-level component.
A `@Qualifier` selects a named component by its bean name.

=== Lifecycle integration

Spring's `SmartLifecycle` drives Axon startup and shutdown when using the Spring Boot Starter.
The `SpringLifecycleStartHandler` and `SpringLifecycleShutdownHandler` integrate Axon's lifecycle phases with Spring's context lifecycle:

* On context startup: Axon's lifecycle phases run in ascending phase order.
* On context shutdown: Axon's lifecycle phases run in descending phase order (reverse startup order).

This means calling `AxonConfiguration#start()` is not required and has no effect in a Spring application.
The lifecycle is managed entirely by the Spring context.

=== Modules in Spring

xref:module.adoc[`Module`] implementations registered via `componentRegistry` work identically in Spring: the `SpringComponentRegistry` treats module registrations the same as in plain Java, preserving the same one-way visibility between a module and its parent.

Axon's built-in modules (for example, the event processor modules registered through `EventProcessorDefinition`) use this mechanism to keep event processor infrastructure isolated from the application's root configuration.
